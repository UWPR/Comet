# Remaining index-memory work and estimated gains

Status: **PLANNED (2026-08-29).** Successor ledger to `docs/20260827_PI_memory.md`, whose
plan (Phases 0-4, the FI_DB SoA port, the streamed `.idx` reader, and the build-path
`g_pvDBIndex` removal) is fully implemented and measured. This document lists what is
left, with the estimated memory gain of each item at the two measured reference scales:

- **tryptic phospho**: `20260420-human-phosho/comet.params`, human canonical target-decoy,
  M x3 + STY x3 -- 4.66M raw peptides / 124.9M variants.
- **target-decoy MHC**: `comet.params.MHC` verbatim, no-enzyme, length 7-25, M-ox x3 --
  398.0M raw peptides / 555.0M variants (build peak 46.4 GB, search peak 32.3 GB as of
  the 2026-08-28 follow-ups).

## 1. Digestion-tuple phase of the index build (the build's binding constraint)

The 45.2 GB peak inside the target-decoy MHC build is the per-thread, per-length
`PepGenTupleShort`/`PepGenTuple` buffers (`g_vvvPepGenShort`/`g_vvvPepGenLong`) holding one
tuple per peptide OCCURRENCE (pre-dedup), plus their sorts. Short-peptide tuples are
already 5-bit-packed 32B structs; long-peptide tuples carry plain sequence buffers, and
everything is occurrence-count-sized. Pooling/packing here is the Phases-1-3 trick applied
to the build's front half.

- Estimated gain: **~10-15 GB off the TD-MHC build peak** (46.4 -> low-30s GB) -- the
  change that would let ~600-700M-peptide builds fit a 54 GB machine.
- Effort/risk: moderate-to-hard -- the multithreaded digestion hot path, with sort
  comparators over those structs.

## 2. `GenerateVariantArray()` staging sort (the search-side load peak)

The 24B/entry `FragmentPeptidesStruct` staging is 13.3 GB at TD-MHC (6.2 GB canonical MHC,
3.0 GB tryptic), held alongside the raw table while it is sorted. Sorting directly into
the 13B/entry SoA would cut the transient by ~11B/entry.

- Estimated gain: **~5-6 GB off the TD-MHC search peak** (32.3 -> ~27 GB); ~1.3 GB at
  tryptic scale.
- Trade-off: requires an explicit sort tie-break, which changes equal-mass candidate
  order -- a one-time, deliberate break of the byte-identical-output guarantee every
  change so far has preserved (arguably an improvement: tie order would become
  deterministic across platforms/STLs). Needs sign-off and a PSM-equivalence validation
  instead of a byte-diff. The byte-identical alternative (external/partitioned merge
  sort) is substantially more complex.

## 3. FI_DB posting list (the largest untouched structure)

`g_iFragmentIndex` is 13.2 GiB at the tryptic phospho benchmark (3.54e9 x 4B entries);
far larger at MHC scales. Bin-local delta + varint encoding could plausibly halve it.

- Estimated gain: **~6-7 GB for FI workloads** at tryptic phospho scale.
- Risk: the decode lands in the single hottest loop in FI search. After the MSVC CMOV
  episode (see docs/20260827_PI_memory.md, cross-platform section), this is a standalone
  project with mandatory before/after Hz gates on native Windows -- not a rider.

## 4. Smaller steady-state items (diminishing returns)

- **5-bit packing of the raw-table sequence pool** (`PackPeptide` machinery exists):
  ~35% of the pool -- ~1.1 GB canonical MHC / ~2.3 GB TD-MHC -- at the cost of a decode in
  `MaterializeOneEntry()`/`AddFragments()`.
- **`PEPTIDE_MOD_SEQ_IDXS` narrowing** (`int32` -> `uint16` when the mod-seq count allows;
  it is 10 at MHC): ~0.76 GB at TD-MHC, near-zero for configs with many mod-seqs.
- **Variant-array bucket directory** (drop the 4B mass key; docs/20260827_PI_memory.md
  Section 4.4): ~2.2 GB TD-MHC steady -- examined and rejected once for CPU risk on
  isotope-enabled searches; still rejected absent new evidence.

## 5. Outstanding verification (not a memory change)

Every recorded number is from batch runs. An RTS-mode spot-measurement (Windows
`RealtimeSearch.exe` or `tests/rts_repro/`) would close the loop with the original
20260730 RTS baselines that motivated the effort. Same structures are shared, so no
surprises are expected.

## Recommendation

If the goal is bigger MHC-class databases on current hardware, item 1 is the next
project -- it is the wall actually hit. Item 2 is cheap but only if the tie-order change
is blessed. Item 3 only if FI memory specifically becomes a problem, as its own gated
effort. Item 4: leave alone. Item 5: cheap, do opportunistically.
