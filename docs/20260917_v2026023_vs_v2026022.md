# v2026.02.3 vs. v2026.02.2: FI_DB and PI_DB batch + RTS benchmark (2026-09-17)

Head-to-head comparison of the two most recent Comet releases on the human canonical
proteome with two variable-mod sets, both index types (FI_DB fragment index, PI_DB peptide
index), both search drivers (batch `Comet.exe`, real-time `RealtimeSearch.exe`), at 4 and 8
threads. `v2026.02.3` is additionally run with Comet's internal decoys (`decoy_search = 1`
against the decoy-free FASTA), which FI_DB did not support before this release
(`docs/20260914_FI_internal_decoys.md`).

Every number below is the mean of 3 repetitions of the same process launch. Rep-to-rep
spread (max/min of the reported Hz) has a median of 1.5% and a worst case of 10.7%
(`v2026.02.3` FI phospho batch, 8 threads), so differences under ~5% are noise.

## Summary

1. **PI_DB searches are 1.7-2.7x faster.** OxMet: 2.4-2.7x (batch and RTS, both thread
   counts). OxMet+phospho: 1.7-1.8x. Same result rows, same 1% FDR PSM counts.
2. **FI_DB index regeneration is 2-3x faster and now scales with threads.** The in-memory
   fragment index for the phospho search took ~65 s to rebuild in `v2026.02.2` regardless
   of thread count; `v2026.02.3` takes 37 s at 4 threads and 25 s at 8. RTS "initialize"
   for FI phospho drops from 71-72 s to 43 s / 30 s. The FI search phase itself is 30-40%
   faster in batch and unchanged-to-10%-faster in RTS.
3. **Memory is lower everywhere.** FI phospho peak 19.9-20.0 GB -> 18.3 GB (target+decoy)
   / 17.9-18.2 GB (internal decoys). PI phospho 7.7-7.9 GB -> 5.1-5.3 GB (target+decoy) /
   2.8 GB (internal decoys, one third of `v2026.02.2`). `.idx` build peak 1.1 GB -> 0.55 GB.
4. **Internal decoys cost nothing.** Search speed equals the target+decoy FASTA within
   noise in all eight pairings; peak memory is lower and the index is half the size
   (2.328e6 vs. 4.659e6 unmodified peptides), so `.idx` builds in 1 s instead of 3-4 s and
   PI RTS initialization halves (21 s -> 10.5 s for phospho).
5. **Results are unchanged for three of the four target+decoy configurations.** OxMet
   FI_DB, OxMet PI_DB and phospho PI_DB batch outputs are PSM-for-PSM identical between
   versions (peptide and xcorr on every one of 41,886 / 61,504 / 61,944 rank-1 rows). FI
   phospho differs on 188 of 44,460 rank-1 peptides (0.4%); PSMs at 1% FDR move from
   16,810 to 16,680 by xcorr (-0.8%) and from 19,713 to 19,860 by E-value (+0.7%).

## Environment and method

- Intel Core Ultra 7 265K (8 P + 12 E cores, 20 threads), 64 GB RAM, Windows 11
  (10.0.26200); driver run from a WSL bash session with nothing else running.
- **Binaries.** `v2026.02.3` = tag `4dc8f775` (`Comet version "2026.02 rev. 3"`), built
  2026-09-17 from the tagged tree. `v2026.02.2` = tag `6edec914` (`"2026.02 rev. 2"`),
  built the same day from a git worktree of that tag. Both: Release/x64, `v143`
  platform toolset (MSVC 14.44), same MSBuild. Each version directory carries its own
  `Comet.exe`, `RealtimeSearch.exe`, `CometWrapper.dll` and the Thermo/OpenMcdf
  runtime DLLs.
- **Query file.** `20240924_Hela_01.raw` (89,593 scans, 63,488 MS2), also passed as the
  MS1 reference file; same file as `docs/20260915_benchmark.md` and the July note.
- **Databases.** `human.canonical.target-decoy.fasta` (40,908 entries; 20,454 targets +
  `DECOY_` reversed) for the target+decoy runs with `decoy_search = 0`;
  `human.canonical.fasta` (20,454 entries) with `decoy_search = 1` for the internal-decoy
  runs (`v2026.02.3` only). Both are the FASTAs used on 2026-09-15.
- **Params.** The 2026-09-15 phospho `comet.params` (trypsin, 2 missed cleavages, MH+
  700-5000, length 7-50, static C+57.021464, 20 ppm precursor, 0.02 fragment bins,
  `fragindex_*` defaults, `max_variable_mods_in_peptide = 3`, AScorePro on in RTS).
  **OxMet** = `variable_mod01 = 15.9949 M 0 3`, no second mod. **OxMet+phospho** = the
  same plus `variable_mod02 = 79.966331 STY 0 3 ... 97.976896`. Only `database_name`,
  `decoy_search` and `num_threads` differ between the four params files.
- **Per configuration:** `Comet.exe -i` (FI) or `-j` (PI) index build x3 (8 threads);
  batch `Comet.exe -Pcomet.params -D<idx> -N<out> <raw>` x3 at 4 and at 8 threads;
  `RealtimeSearch.exe <raw> <raw> <idx> <threads> 1 <1=FI|0=PI>` x3 at 4 and at 8 threads.
  Twelve configurations, 180 runs total, run strictly sequentially in one script.
- **Metrics** are the programs' own lines: batch `- searching "..." ... Ns (spectra,
  ms/spec, Hz)` and `- done. (total, peak)`; RTS `initialize` / `raw file preload` /
  `MS2 search elapsed time`, `MS2 average search time ... Hz` and the final `Done. (GB)`.
  Peak memory is `CometSearchManager::GetPeakMemory()` in both drivers. External wall
  clock was recorded around every process and agrees with the reported totals to
  within 1-2 s (process start-up + `.raw` open).

## Observations

1. **PI_DB.** The 2.4-2.7x OxMet and 1.7-1.8x phospho gain lines up with the
   index-memory work between the tags (`docs/20260827_PI_memory.md`: `b8e24444` 13-byte
   SoA variant array with a fixed-point mass key, `22fcba72` pooled raw-peptide table,
   `b3dca492` flat-pooled mod tables, `51a61b6c` uint32 protein-list ordinals) and the
   correctness/performance batch in `#128` (`6b7d6649`). Fewer bytes per candidate means
   the mass-window scan that dominates PI_DB is far more cache-friendly. Init time is
   unchanged (variant generation is the same work); the whole gain is in the search
   phase, so it shows equally in batch and RTS. This note measures the aggregate; it does
   not apportion the gain between those commits.
2. **FI_DB regeneration.** In `v2026.02.2` the fragment-index build took 64-66 s in every
   phospho run regardless of `num_threads`. In `v2026.02.3` it takes 34-37 s at 4 threads
   and 22-25 s at 8, so it now has a thread dependence, and the `.idx` read is streamed
   (`1913b4eb`). For an RTS session this is the time-to-first-spectrum: 72 s -> 30 s for
   phospho at 8 threads. The FI search phase gains 30-40% in batch (the 13-byte FI variant
   array `2facbc2c`, and the binary-search fix, walk fast path and prefetch in `35fb9b01`)
   but only ~10% in RTS; the likely reason is that RTS's fixed per-call work (query
   preprocessing, AScorePro, result marshalling) dilutes a candidate-walk speed-up, but
   that was not profiled here.
3. **Memory.** FI phospho drops 1.6 GB (8%) because the ~14 GB posting list (4 B x
   3.54e9) is unchanged and only the variant array, raw table and mod pool shrank. PI
   phospho drops from 7.7 to 5.1 GB (34%) because the variant array *is* the dominant
   structure there. With internal decoys the PI variant array holds only the 62.5M target
   variants and decoys are pseudo-reversed on the fly, so PI phospho peaks at 2.8 GB.
4. **Internal decoys** (Table 2/3, third column group vs. second) are speed-neutral: the
   fragment index has the same 1.249e8 variants and 3.54e9 postings either way, and PI_DB
   scores the same number of candidates. They halve the `.idx`, halve PI init and shave
   5-6 s off FI init. The rank-1 decoy fraction and the 1% FDR PSM counts agree with the
   FASTA-decoy runs within 1%.
5. **FI phospho result drift.** The 188 changed rank-1 peptides (0.4%) between versions
   are confined to FI_DB with the phospho mod set; the OxMet FI run and both PI runs are
   identical, so the cause is in FI-specific mod handling rather than scoring. Candidates
   in the range: the FI mod-slot / neutral-loss fixes verified by T25/T26
   (`docs/20260819_fablereview.md`), and the `ModificationsPermuter` rewrite for terminal
   mods (`#130`) which changed variant enumeration order and therefore tie-breaking among
   equal-xcorr phospho-site isomers. Net PSM yield at 1% FDR is -0.8% by xcorr and +0.7% by
   E-value, both inside the 5% same-version tolerance the T23/T24 harness uses.
6. **Thread scaling** is unchanged in character: FI search is ~1.8x from 4 to 8 threads in
   both versions and both drivers; PI ~1.7x batch / ~1.8-2.0x RTS. Only the FI
   regeneration phase gained a thread dependence.
