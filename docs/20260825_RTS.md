# Comet master (2026.02 rev. 2) vs. v2026.02.1 — RTS Performance Re-Analysis

Reproduction of [`notes/20260729_RTS_2026021.html`](https://uwpr.github.io/Comet/notes/20260729_RTS_2026021.html)
against current `master` (commit `6b7d6649`, "correctness fixes, memory-safety hardening,
RTS/FI performance (#128)", 2026-08-23), compared to the original v2026.02.1 tag
(`530ce9f2`, 2026-07-28) and — where the original doc reported it — v2026.02.0.

## Hardware & environment

Identical to the original report — same physical machine, confirmed via the registry
(`Intel(R) Core(TM) Ultra 7 265K`, 8 P-cores + 12 E-cores = 20 threads, no
hyperthreading, 64GB RAM, Windows 11). All `.raw` spectra read from
`20260420-human-phosho/` and preloaded into memory before timed search phases begin
(same methodology as the original).

## Methodology notes / what changed since the original report

- **`.idx` format is not compatible across versions** (per this repo's own T23/T24 test
  design), so a fresh `.idx` was built with master's own `Comet.exe -i`/`-j` for each
  config rather than reusing the v2026.02.1-built `.idx` files.
- **PI vs FI is now a build-time choice baked into the `.idx`, not a runtime flag.**
  `Comet.exe -i` builds an `IndexSearchType: fragment ion index` `.idx`;
  `-j` builds `IndexSearchType: peptide index`. `RealtimeSearch.exe`'s
  `index_search_type` CLI argument is now effectively vestigial once an index exists —
  the file's own header determines which path runs. This is a real architecture change
  (`819171b7`, "Reduce PI memory ~1.6x and unify PI/FI on one .idx format") relative to
  the runtime-switchable model the original report used. Discovered here after an initial
  PI_DB run silently re-ran as FI_DB; a `-j`-built `.idx` was required to get genuine
  PI_DB numbers.
- **The "pure search-call time" instrumentation the original report isolated from
  wall-clock (its `MS2 pure search-call time` console line) no longer exists** in
  current master's `RealtimeSearch/SearchMS1MS2.cs`. Only wall-clock throughput
  (`watchParallelPhase`-derived Hz) is available now, so the "Pure Search-Call Time
  Analysis" section of the original report is not reproduced here — there is nothing
  to isolate it from anymore on the master side.
- Same two mod-space configs, same `comet.params` files (copied byte-identical from the
  original benchmark rig at `/mnt/c/Work/20260730-phospho-v2026020-vs-v2026021/`), same
  `.raw` files:
  - **Run 1 (wide)**: `20240924_Hela_01.raw`, 63,488 MS2 scans; M/STY variable mods, up
    to 3/type and 3 total; mass 700–5000; length 7–50.
  - **Run 2 (narrow)**: `20250520_Hela_06.raw`, 49,844 MS2 scans; M/STY up to 2/type
    and 4 total; mass 800–5000; length 8–50.
  - Database: `human.canonical.target-decoy.fasta` (same file both sessions).

## PSM-count investigation: is the drop real?

Both configs show fewer PSMs@1%FDR on master than v2026.02.1 (narrow: -4.2% XCorr /
-2.2% E-value; wide: -6.0% XCorr / -3.3% E-value). This was checked directly rather than
assumed:

1. **Ruled out as a params/config artifact.** Both `comet.params` files were copied
   byte-identical from the original benchmark rig. Master's fresh `comet.params.new`
   defaults were diffed against both configs — `isotope_error`, the `fragindex_*`
   block, mod counts, and mass/length ranges either match explicitly or fall back to
   identical defaults where a field was absent (the narrow config predates the
   `fragindex_*` block in the params schema, but master's built-in defaults for those
   fields match what the wide config sets explicitly).

2. **Direct PSM-level diff** (`qvalue.py --diff` between v2026.02.1's and master's
   narrow batch output, 1% FDR, XCorr sort):
   - **795 PSMs unique to v2026.02.1** — all targets (0 decoys), xcorr clustered
     tightly at 1.50–1.56, i.e. all marginal calls right at the old cutoff.
   - **100 PSMs unique to master** — also all targets, but at xcorr **1.57 up to
     3.36** (several well above 2.0) — spectra v2026.02.1 never identified *at all*,
     not just below its own cutoff.

   The second bucket is the key evidence: master finds genuinely new, high-confidence
   correct matches v2026.02.1's search missed entirely, while the empirical XCorr
   cutoff for 1% FDR also rose (1.498→1.565 narrow), dropping some marginal
   near-cutoff calls. Net effect is fewer PSMs despite better match quality.

3. **Full commit-level bisection.** The initial hypothesis was that this was all PR
   #128 ("correctness fixes, memory-safety hardening, RTS/FI performance", squash-merged
   as `6b7d6649`). That turned out to be incomplete: most of the xcorr movement predates
   PR #128 entirely. Isolating the true cause required checking out and rebuilding each
   individual commit between v2026.02.1 and master, since `6b7d6649` itself is a single
   squash-merge commit with no internal git history — the granular pre-squash commits
   were recovered from the `fablereview` branch (`git log f030607b..a4dc6a1c`, verified
   to be the exact ancestor chain squashed into `6b7d6649` for `CometSearch/`/
   `CometWrapper/` content, module one incidental divergence noted in the table below).
   Each commit was built in an isolated `git worktree` (`CometSearch`+`Comet` targeted
   MSBuild rebuild, ~30-60s) and run through the same narrow-config batch search
   (`20250520_Hela_06.raw`, ~25-60s depending on whether the fragment-index build was
   parallelized yet at that commit) and `qvalue.py` at 1% FDR:

   | Step | Commit | xcorr@1%FDR | evalue@1%FDR | Δxcorr | Δevalue | What changed |
   |---|---|---|---|---|---|---|
   | v2026.02.1 baseline | `530ce9f2` | 16,428 | 17,757 | — | — | original tag |
   | #121 PI/FI unify | `819171b7` | 16,428 | 17,757 | 0 | 0 | **byte-identical**, confirmed |
   | #122 FI mod-slot bug fix | `ffc8b248` | 15,800 | 17,289 | **-628** | **-468** | real fix, real effect |
   | #124 Phase 0.5 regen | `1fff1db2` | 15,800 | 17,289 | 0 | 0 | no effect |
   | #125 restore `.idx` | `6edec914` | 15,800 | 17,289 | 0 | 0 | no effect |
   | #126 wide fit window | `a0f7a20c` | 15,800 | 16,734 | 0 | **-555** | evalue-only (`LinearRegression`) |
   | #127 CometWrapperCore | `f030607b` | 15,800 | 16,734 | 0 | 0 | unrelated addition, no effect |
   | PR128 B1-B13/C1-C13 | `5cc3be9b` | 15,733 | 17,306 | **-67** | **+572** | real fix, confounded (see caveat) |
   | PR128 decoy_prefix + B9/Section3 | `194ef3e7`+`31b3575a` | 15,733 | 17,306 | 0 | 0 | no effect on this FI_DB/no-ascorepro config |
   | PR128 perf (P1-P11, 7 commits) + Copilot-review fixes | …→`510888c9` | 15,733 | 17,306 | 0 | 0 | **confirms the "byte-identical output" perf claims** |
   | actual squash-merge state | `6b7d6649` (= master) | **15,733** | **17,373** | 0 | +67 | matches current master exactly |

   The arithmetic closes exactly: xcorr -628-67 = **-695** (16,428→15,733 ✓.); evalue
   -468-555+572+67 = **-384** (17,757→17,373 ✓).

   **Findings:**
   - **The xcorr drop is not PR #128 — it is almost entirely commit `ffc8b248` (#122,
     "Fix FI compacted variable-mod-slot index bugs")**, which landed *before* PR #128
     started. Attributing this to PR #128, as an earlier draft of this document did, was
     wrong.

     **What the bug actually was.** `MOD_NUMBERS[modNumIdx].modifications[]` (aliased
     `mods` at each call site) stores 0-based indices into a *compacted* list of only
     the currently-active variable-mod slots
     (`CometPeptideIndex::GetVModSlotForAllModsIdx()`) — e.g. if only
     `variable_mod02`/`variable_mod04` are active, compacted index 0 means real slot 1
     and compacted index 1 means real slot 3. Four FI_DB call sites —
     `CometFragmentIndex.cpp`'s `AddFragments()` (both its precursor-mass loop and its
     fragment-ion b/y-mass loop) and `AddFragmentsThreadProc()` (protein-mod-filter
     check), plus `CometSearch.cpp`'s `SearchFragmentIndex()` (the actual FI_DB
     per-query scoring function, called on *every* FI_DB search hit) — instead used
     `mods[]`'s values directly (or with a naive `- 1`) as if they were raw
     `varModList[]` slot numbers. `CometPeptideIndex.cpp`'s `MaterializeOneEntry()`
     (the PI_DB equivalent) already did the translation correctly, confirming PI_DB was
     unaffected and this was FI_DB-specific throughout. Two distinct failure modes rode
     on this one root cause:
     - **Wrong-mass corruption.** Whenever the compacted and real slot numbering
       actually diverge (any config with a "gap" — some `variable_modNN` before the
       last active one left unset), the precursor mass and the modified fragment-ion
       masses fed straight into XCorr/SP scoring were silently computed against the
       *wrong modification's mass*. One instance read `varModList[mods[j] - 1]`, which
       is `varModList[-1]` (undefined behavior) whenever the first configured
       variable-mod type applied.
     - **Heap-buffer-underflow via a missing `-1` guard.** `mods[j] == -1` is the
       ordinary "this candidate residue wasn't chosen as modified in this particular
       combinatorial variant" sentinel — routinely produced whenever a peptide has
       *more* modifiable candidate sites than `max_variable_mods_in_peptide` allows
       (a completely standard config, not an edge case — e.g. 3 candidate S/T/Y
       residues with only 2 phospho slots allowed). The b/y-ion mass loop was missing
       a `mods[j] != -1` guard that an equivalent check 30 lines above, in the same
       function, already had; casting `-1` to `size_t` produced a huge index into
       `vModSlotForAllModsIdx`, an out-of-bounds read. Confirmed via AddressSanitizer;
       under plain `-O3` it read a "harmless" garbage value rather than visibly
       crashing, which is why it went undetected.

     **What actually counts as a "gap".** Not every unusual `variable_modNN` slot
     assignment triggers the wrong-mass failure mode — `CometSearchManager.cpp` runs a
     separate, earlier "reduce variable modifications if entries are the same" merge
     pass (well before `GetVModSlotForAllModsIdx()` ever runs) that folds two
     *identically-configured* mods on different slots into one. E.g.
     `variable_mod01 = 80.0 S` + `variable_mod02 = 80.0 T` (same mass, same neutral
     loss/site-limits/term-distance) get merged into a single real slot 0 covering
     `"ST"` — `strcat()`s `varModList[1]`'s residue char onto `varModList[0]` and blanks
     `varModList[1]` (`szVarModChar = "-"`, `dVarModMass = 0.0`) outright. By the time
     `GetVModSlotForAllModsIdx()` runs, slot 1 is indistinguishable from a slot that was
     never configured at all, so this reduces to a single active mod at real slot 0 —
     compacted index 0 and real slot 0 coincide trivially, and even the *pre-fix* buggy
     code would have gotten this specific case right by coincidence. The bug needs mods
     that *don't* merge (different mass, or any other matched field differs) with an
     earlier slot left genuinely unconfigured — e.g. `variable_mod01` left blank while
     `variable_mod02` carries the real, distinct modification, exactly the example in
     `ffc8b248`'s own commit message.

     Neither of this benchmark's two configs has a literal "gap" (narrow: `M` in slot
     0, `STY` in slot 1, both active, contiguous; wide: same layout) — so the
     wrong-mass failure mode's headline scenario doesn't directly apply here. The
     `-1`-sentinel failure mode is the far more plausible driver of the measured -628:
     it fires on *any* peptide whose candidate-site count exceeds the per-combination
     mod cap, which a full human-proteome tryptic digest with real phospho/oxidation
     mod settings hits constantly, and the `SearchFragmentIndex()` instance of the bug
     runs on every single FI_DB-scored hit, gap or no gap — exactly consistent with a
     broad, dataset-wide scoring effect rather than a narrow edge case. The fix was
     validated with two new regression tests (`t25_fi_mod_slot_gap`,
     `t25_fi_mod_slot_ambig` — the latter AddressSanitizer-confirmed) and consolidated
     the previously six hand-duplicated translation call sites into two shared,
     bounds-checked helpers (`TranslateVarModSlot()`, `PassesVarModProteinFilter()`) so
     a future copy can't silently drop the guard again.
   - **The evalue drop is compound**, from two unrelated mechanisms: #122's matching
     fix, and #126's `LinearRegression` fit-window widening (evalue-only by
     construction, since it only affects the E-value tail-fit, not xcorr ranking).
   - **A genuine git-history quirk**: `5cc3be9b` (PR #128's big correctness commit)
     incidentally reverted #126's wide fit window back to the old narrow
     `iStartCorr = iNextCorr - 5` form, as a side effect of patching an unrelated
     log10/cumulative-count bug in the same function
     (`CometPostAnalysis::LinearRegression`). fablereview's own branch tip
     (`510888c9`) still carries that regression. The actual squash-merge into master
     (`6b7d6649`) does **not** — its `CometPostAnalysis.cpp` has the wide-window form
     intact, confirmed by diffing `6b7d6649` against `510888c9` directly and by
     substituting master's actual file into the `510888c9` build (reproduces
     15,733/17,373 exactly). So master itself never regressed on this axis; only an
     intermediate, never-shipped branch state did.
   - **Every purely-performance commit in PR #128** (`5b4683df` P1, `7d5aabc4` P9-P11,
     `66aa83bd` P4-P7, `2ff55bf1` P2/P3, plus the two Copilot-review leak/safety
     commits `4c8d2d69`/`510888c9`) verified **zero** PSM-count effect — confirming
     their own commit-message claims of "byte-identical output" empirically rather
     than by trusting the message.
   - **Decoy-prefix/PI_DB-decoy-misclassification (`194ef3e7`) and B9/Section-3
     (`31b3575a`)** show zero effect here — expected, since those are PI_DB-specific
     or AScorePro-specific and this config is FI_DB with AScorePro off.
   - **Not fully decomposed**: `5cc3be9b` bundles ~26 named sub-fixes (B1-B13 wrong-
     result bugs + C1-C13 crash/UB fixes) in one commit. Isolating individual
     sub-fixes within it would need manual per-hunk reverse-patching, not git-commit
     bisection — not done here, since its net effect (-67 xcorr) is small relative to
     #122's.

This magnitude (2–6%) is within the project's own accepted cross-version tolerance —
`CLAUDE.md`'s T23/T24 design note uses a 10% baseline-comparison tolerance specifically
because *"a different Comet version legitimately identifies a somewhat different
peptide population."* **Conclusion: the drop is real, not fixable via any parameter,
and traceable to two specific commits (`ffc8b248` for xcorr, `ffc8b248`+`a0f7a20c` for
evalue) rather than PR #128 as a whole.**

also why PI_DB reports far more raw scored lines than FI_DB for the same spectra).

## Summary

- **RTS throughput roughly doubles** at 8/20 threads vs. v2026.02.1 in both mod-space
  configs, with smaller but real gains at 1-4 threads.
- **Batch FI generation is 2.6-3.5x faster**, driving total batch search time down by
  more than half.
- **PI_DB is dramatically faster and lighter** (70-85% higher Hz, ~33% less memory)
  following the PI/FI index-format unification.
- **`.idx` files are 2.4-3.5x smaller.**
- **PSM@1%FDR counts dropped 2-6%** — confirmed real (not a config artifact) via a
  full commit-level bisection. Contrary to an earlier hypothesis, this is **not**
  primarily PR #128: the xcorr drop traces almost entirely to one pre-#128 commit
  (`ffc8b248`, "Fix FI compacted variable-mod-slot index bugs"), and the evalue drop
  is compound (`ffc8b248` + `a0f7a20c`'s E-value fit-window widening). Every
  performance-only commit in PR #128 verified as exactly PSM-count-neutral. Within
  the project's own accepted cross-version tolerance.
- **Architecture changed**: PI vs FI is now chosen at `.idx` build time, not RTS runtime;
  the harness's pure-search-call-time instrumentation was removed (wall-clock only now).
