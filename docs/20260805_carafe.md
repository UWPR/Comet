# Carafe-predicted fragment ion index: goal and implementation plan

Status: **PLANNING -- design decisions finalized (Section 8), implementation not started.** This
document defines the goal, walks the existing Carafe/Comet code this touches, and lays out a
phased plan (Section 6). All design questions raised during planning are resolved; see Section 8
for the decisions and their rationale.

## 1. Goal

Today, `CometFragmentIndex::AddFragments()` inserts **every** b/y ion (from ion length 3 up to
`length-1`, singly charged only) of **every** modified-peptide variant into the fragment ion
index (FI). That is exhaustive and mod-agnostic -- it has no notion of which fragments a real
spectrum for that peptide would actually produce.

The goal of the `carafe` branch is to replace that exhaustive population with a **predicted**
one:

1. Export the peptide+mod universe of a built `.idx` (PI_DB) to Carafe via `tools/idx_to_carafe.py`
   (already implemented on this branch).
2. Run Carafe's `ai_pred.py` MS2 model over that universe to predict a relative-intensity
   spectrum (b/y, charge 1 and 2) for every peptide variant.
3. Keep only the peaks at or above some relative-intensity threshold vs. the base peak (user
   specified this as 10% to start).
4. Populate the FI using **only** the kept (predicted, high-intensity) fragments instead of the
   full exhaustive set.

Expected payoff, quantified against real numbers already measured on this codebase
(`docs/20260730_PI_reduction.md`, Section 1): for one real FI_DB build, `g_iFragmentIndex` (the
flat posting-list array) alone was **13.78 GiB out of a 19.0 GB total FI_DB memory footprint** --
by far the largest single structure in the index. Trimming the average number of kept fragments
per peptide directly shrinks that array (memory), and every per-query bin lookup during search
walks a shorter posting list at that fragment mass (speed) -- both benefits scale with however
much the 10%-threshold actually reduces fragment count in practice (not yet measured; see
Testing section).

## 2. Relevant existing code (read before implementing)

### 2.1 How the FI is populated today

`CometFragmentIndex::GenerateFragmentIndex()` (`CometSearch/CometFragmentIndex.cpp:169`) runs a
two-pass build over `g_vRawPeptides` (unique unmodified peptides) x every valid mod-variant
(enumerated by `AddFragmentsThreadProc()`/`PermuteIndexPeptideMods()`):

- **Pass 1 (count, `bCountOnly=1`)**: for every `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)`
  variant, `AddFragments()` computes the variant's mass, appends a `FragmentPeptidesStruct` to
  `g_vFragmentPeptides`, and increments a per-mass-bin counter in `g_iFragmentIndexOffset[]` for
  every b/y ion it would insert.
- Between passes, **`g_vFragmentPeptides` is sorted by `dPepMass`** (`CometFragmentIndex.cpp:214`).
  The variant's position in this sorted vector becomes its `iWhichFragmentPeptide` -- the value
  actually written into the FI posting list.
- **Pass 2 (fill, `bCountOnly=0`)**: re-runs `AddFragments()` per (now sorted-index) variant,
  writing `iWhichFragmentPeptide` into `g_iFragmentIndex[]` at each b/y ion's CSR write position.

Inside `AddFragments()` (`CometFragmentIndex.cpp:409`), the ion loop is:

```cpp
for (int i = 0; i < iEndPos; ++i)   // iEndPos = peptide length - 1
{
   dBion += <residue i mass>;               // cumulative -> b-ion of length i+1
   dYion += <residue iEndPos-i mass>;        // cumulative -> y-ion of length i+1
   ...
   if (i > 1)   // *** first two ion lengths (1, 2) are never indexed, at any intensity ***
   {
      // insert dBion into FI (charge 1 only -- no charge-2 b/y ion is ever indexed today)
      // insert dYion into FI (charge 1 only)
   }
}
```

Two things to note for the plan below:

- **Only charge-1 b/y ions exist in the FI at all.** There is no charge-2, no neutral-loss, no
  a-ion. Carafe's `b_z2`/`y_z2`/`*_modloss_*` channels are irrelevant to *what gets inserted*,
  but they do matter to *how the base peak is defined* -- it's the max over all predicted
  channels, not just the insertable ones (Section 8, item 3).
- **Ion lengths 1 and 2 are already unconditionally excluded**, independent of any Carafe
  prediction. The mask only ever needs to cover lengths 3..(peptide length - 1).

### 2.2 Where PI_DB and FI_DB diverge on the compact variant array

`CometPeptideIndex::WritePeptideIndex()` (`CometSearch/CometPeptideIndex.cpp:815`) writes a
"compact variant array" section to the `.idx` (one `(dPepMass, iWhichPeptide, modNumIdx,
cNtermMod, cCtermMod)` tuple per variant, **sorted by mass**) via its own enumeration path,
`EnumerateIndexPeptideMods()`. This is what `tools/idx_to_carafe.py`'s `iter_variants()` reads.

Per the comment directly above that write (`CometPeptideIndex.cpp:1099`):

> `FI_DB` mode ignores it and regenerates its own posting list from the permutation tables above
> ... unchanged from before this unification.

I.e. **FI_DB never reads the compact variant array.** When a `.idx` is opened in FI_DB mode,
`CometFragmentIndex::AddFragmentsThreadProc()` independently re-enumerates variants from the same
persisted `MOD_SEQS`/`MOD_NUMBERS`/`PEPTIDE_MOD_SEQ_IDXS` tables, and re-sorts by mass itself.
This is `EnumerateIndexPeptideMods()` and `AddFragmentsThreadProc()` -- two separately maintained
enumeration code paths over the same input tables, not one shared function. That matters directly
for how a mask must be keyed (Section 4.1, pitfall 1).

### 2.3 Carafe's prediction output shape

`ai_pred.py`'s `predict_ms2()` (`Carafe/src/main/resources/py/v2/ai_pred.py:38`) takes a
`sequence`/`mods`/`mod_sites`/`charge` TSV/parquet (exactly `idx_to_carafe.py`'s output schema)
and writes three row-aligned outputs per batch:

- `<prefix>_ms2_df.tsv` -- the input rows echoed back, augmented with `frag_start_idx`/
  `frag_stop_idx` (AlphaBase/peptdeep convention: each precursor occupies `nAA-1` contiguous rows
  in the two files below).
- `<prefix>_ms2_pred.tsv` -- the flat fragment table, columns `b_z1`,`b_z2`,`y_z1`,`y_z2`
  (general mode; phospho mode adds `*_modloss_*`), **relative intensities**, one row per
  cleavage site across all peptides (sliced by `frag_start_idx:frag_stop_idx`).
- `<prefix>_ms2_mz_df.tsv` -- the same shape, but m/z instead of intensity (not needed for this
  project -- Comet already computes its own fragment m/z deterministically and does not need
  Carafe's).

AlphaBase's row `r` (0-indexed, `r = 0 .. nAA-2`) for a peptide of length `nAA` corresponds to
cleavage after residue `r+1`: **`b` column of row `r`** is `b_{r+1}` (length `r+1`), **`y` column
of row `r`** is `y_{nAA-r-1}` (length `nAA-r-1`).

## 3. Proposed end-to-end pipeline

```
FASTA --(comet.exe -j)--> PI_DB .idx
         |
         v
tools/idx_to_carafe.py  --> peptide/mods/mod_sites/charge TSV  (one row per FI variant)
         |
         v
Carafe: java -jar carafe.jar ... / ai_pred.py --tf_type ms2 --mode general
         |
         v
  <prefix>_ms2_df.tsv (frag_start_idx/frag_stop_idx) + <prefix>_ms2_pred.tsv (intensities)
         |
         v
tools/carafe_ms2_to_fi_mask.py  (NEW)
   - per variant: base peak = max over ALL predicted channels (b_z1,b_z2,y_z1,y_z2[,modloss])
   - keep (position, ion_type) where intensity >= threshold * base peak (threshold configurable, default 0.10)
   - top up to FRAGINDEX_CARAFE_MIN_KEPT_PEAKS (default 6) most intense eligible fragments if fewer passed
   - remap AlphaBase row -> Comet ion-length index (b: row i; y: mirror row nAA-2-i)
   - drop ion lengths 1,2 (never indexed anyway)
   - key each variant by (iWhichPeptide, modNumIdx, cNtermMod, cCtermMod) -- NOT row position
         |
         v
   fragment mask file, fingerprinted to the source .idx
         |
         v
comet.exe -i (FI_DB build) with new param pointing at the mask
         |
         v
   reduced FI_DB .idx  -->  search (batch or RTS)
```

Backward compatible by construction: no mask configured -> current exhaustive behavior,
unchanged.

## 4. Component-by-component plan

### 4.1 `tools/idx_to_carafe.py` changes

- Add a stable variant-identity column to the output (or a parallel `.idx`-order sidecar) --
  the natural choice is `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)`, i.e. exactly the
  fields the compact variant array already stores. **Do not** rely on output row order/position
  as the key (see pitfall 1 below).
- Current default behavior collapses identical `(sequence, mods, mod_sites, charge)` rows from
  different `(iWhichPeptide, modNumIdx, ...)` tuples (`seen` dedup set,
  `tools/idx_to_carafe.py:576`). That is correct for a Carafe *training/prediction* input (no
  reason to predict the same spectrum twice), but the mask-building step needs to fan the
  single prediction back out to every tuple that mapped to it. Either keep dedup and carry a
  `list[tuple]` per unique row, or add a `--no-dedup`-equivalent default specifically for this
  workflow. Recommend: keep dedup for compute efficiency, emit a side mapping file
  (`dedup_key -> [tuples]`) so the mask builder can broadcast one prediction to every tuple that
  shares it.
- Charge column: currently emits 2 rows per variant (`--charges 2,3` default) since
  `idx_to_carafe.py` was written for spectral-library generation, where every precursor charge
  state matters. For *this* use case, b/y ion m/z is charge-independent and only the model's
  intensity output can vary by charge -- keep both configured charges' rows; the mask builder
  takes the per-fragment max across them (Section 8, item 1).

### 4.2 New tool: `tools/carafe_ms2_to_fi_mask.py`

Reads `<prefix>_ms2_df.tsv` (for `frag_start_idx`/`frag_stop_idx` and the tuple-identity column
added in 4.1) + `<prefix>_ms2_pred.tsv` (intensities), and for every variant:

1. Slice its `nAA-1` rows out of `_ms2_pred.tsv`, once per predicted charge state (per the
   decision on open question 1: predict at each configured charge, e.g. 2 and 3, and take the
   **per-fragment max intensity across charges** before thresholding -- `b_z1[r] = max` over
   the configured charges' `b_z1[r]` values, etc.).
2. Compute the base peak: the single most intense value across **every** predicted channel for
   that variant (`b_z1`, `b_z2`, `y_z1`, `y_z2`, plus `b_modloss_z1/z2`/`y_modloss_z1/z2` in
   phospho mode) -- i.e. the true predicted-spectrum base peak, not restricted to whichever
   channels the FI can actually insert (open question 3, decided). A peptide whose real dominant
   fragment is charge-2 will correctly threshold its charge-1 ions against that higher reference,
   even though the charge-2 ion itself is never written to the FI.
3. For each AlphaBase row `r` (0-indexed): candidate-keep `b_{r+1}` if
   `b_z1[r] >= threshold * base_peak` (**only if `r+1 >= 3`**, i.e. skip AlphaBase rows 0,1);
   candidate-keep `y_{nAA-r-1}` similarly from the `y` column of the **mirrored** row (see
   pitfall 2) (only if `nAA-r-1 >= 3`).
4. **Minimum-fragment floor** (open question 4, decided): if fewer than
   `FRAGINDEX_CARAFE_MIN_KEPT_PEAKS` candidate-eligible (length >= 3) fragments cleared the
   threshold in step 3, top-up by intensity (across the combined pool of eligible b and y
   candidates, not a fixed b/y split) until either `FRAGINDEX_CARAFE_MIN_KEPT_PEAKS` are kept or
   every eligible fragment for that variant is kept (whichever comes first -- a variant with
   only 4 eligible fragments total keeps all 4, it does not pad to 6). Named constant lives in
   `CometSearch/core/Constants.h`, alongside the existing `FRAGINDEX_MIN_IONS_SCORE`/
   `FRAGINDEX_MIN_IONS_REPORT` etc. (`CometSearch/core/Params.h:81-82`); default **6**.
5. Pack the per-variant result as two bitmasks (b-kept, y-kept), each up to
   `MAX_PEPTIDE_LEN-1 = 50` bits (`CometSearch/core/Constants.h:24`) -- fits in one `uint64_t`
   each.
6. Write `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod) -> (bMask: u64, yMask: u64)` to a mask
   file, fingerprinted against the source `.idx` (Section 4.3).

**Threshold and floor are both CLI flags** on this tool (`--min-relative-intensity 0.10`,
`--min-kept-peaks 6`, matching the `FRAGINDEX_CARAFE_MIN_KEPT_PEAKS` default), not hardcoded
(open question 5, decided). To make re-sweeping either one cheap, `_ms2_pred.tsv`/
`_ms2_mz_df.tsv` (Carafe's raw per-fragment intensity output) should be treated as the durable
artifact of the expensive GPU inference step -- rerunning `carafe_ms2_to_fi_mask.py` at a new
threshold or floor re-reads those files directly rather than re-invoking `ai_pred.py`.

This is the step that needs a dedicated correctness unit test before it touches real data --
see Section 7.

### 4.3 Mask file format

- New standalone file (not folded into the `.idx` itself -- keeps this experimental feature from
  touching the recently-stabilized unified `.idx` format of `docs/20260730_PI_reduction.md`,
  and lets a mask be regenerated/tuned without rewriting the (large) `.idx`).
- Header: path/hash of the source PI_DB `.idx` (e.g. its `NumPeptides:` count + raw-peptide-table
  byte size, or a full checksum) so a mismatched mask is rejected at load time with a clear error
  rather than silently corrupting the FI build (see pitfall 4). This directly guards against the
  "regenerate the same FASTA into a new `.idx`" trap: `iWhichPeptide`/`modNumIdx` numbering is
  **not** guaranteed stable across independent `.idx` builds, only across *reads of one already-
  built `.idx` file*.
- Body: sorted `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)` -> `(bMask, yMask)` records,
  binary-searchable (or loaded into an `unordered_map`/open-addressed table keyed by a packed
  96-bit tuple) at FI build time.
- A variant with no entry in the mask (peptide skipped by `idx_to_carafe.py`, e.g. unresolved
  mod name, or outside Carafe's trained range) falls back to **fully unfiltered** for that
  variant (open question 2, decided).

### 4.4 `CometFragmentIndex.cpp` integration

- Load the mask (if configured) once, alongside `g_vRawPeptides`/`MOD_SEQS`/`MOD_NUMBERS`, before
  `GenerateFragmentIndex()` runs.
- In `AddFragments()`, right before each of the two `if (dBion > ... && dBion < ...)` /
  `if (dYion > ... && dYion < ...)` insertion blocks (`CometFragmentIndex.cpp:590`/`612`), add a
  mask lookup gated on `i > 1` (matches the existing skip) using the *same* tuple key
  `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)` already available as this function's
  parameters, checking bit `(i - 2)` (or however lengths 3.. get indexed into the 50-bit mask)
  of the b- or y-mask respectively.
- **The count pass and the fill pass must apply byte-identical mask logic.** They already share
  one `AddFragments()` body gated by `bCountOnly`, so as long as the mask check sits *before*
  the `bCountOnly` branch (applies to both), this falls out naturally -- but it is worth an
  explicit code-review note/assertion, since a count/fill mismatch here doesn't crash cleanly;
  it silently overflows or underflows the CSR write-position array (`s_iWritePos`), corrupting
  unrelated mass bins. This is the single highest-severity correctness risk in the whole feature
  and deserves its own test (Section 7).

### 4.5 `comet.params` / CLI / RTS plumbing

- New `comet.params` key, e.g. `fragment_index_predicted_mask_file` (empty = disabled, matching
  the `dFragIndexMinMass`/`iFragIndexSkipReadPrecursors` naming convention already in
  `CometSearch/core/Params.h`).
- Since FI generation is shared between the batch build path and RTS's
  `InitializeSingleSpectrumMS1Search()`/equivalent MS2 init path (per `CLAUDE.md`'s threading
  table, the FI globals are "read-only after init" for both), this needs the same
  `CometSearchManager` -> `CometWrapper` -> `RealtimeSearch/Search.cs` plumbing that
  `index_search_type` got in the PI_DB/FI_DB unification -- new `SetParam()` call site(s) mirror
  that precedent.

## 5. Critical implementation pitfalls (found while reading the existing code)

1. **Positional/row-index keying would be wrong.** FI_DB regenerates `g_vFragmentPeptides`
   independently of the PI_DB's on-disk compact variant array (Section 2.2) via a *different*
   enumeration function, then re-sorts by mass. There is no guarantee this reproduces the exact
   row order `idx_to_carafe.py` read from the compact variant array. The mask **must** be keyed
   by the content tuple `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)`, never by a row index
   or position in any exported/predicted file.
2. **AlphaBase row <-> Comet ion index is not a straight 1:1 mapping.** Comet's loop iteration
   `i` produces `b_{i+1}` **and** `y_{i+1}` (same *length*, computed via a forward+backward
   two-pointer sweep) -- not the complementary cleavage-site pair. AlphaBase's row `r` instead
   produces `b_{r+1}` and `y_{nAA-r-1}` (complementary cleavage-site pair, standard convention).
   So Comet's `y_{i+1}` lives in AlphaBase row `nAA-2-i`, not row `i`. Getting this wrong doesn't
   crash -- it silently keeps/drops the wrong y-ions, a purely quality-degrading bug that would
   be very hard to notice without a targeted test.
3. **Only lengths >= 3 are ever indexed** (`i > 1` gate, independent of any mask). Mask bits for
   length 1-2 are meaningless; the mask builder should either omit them or the consumer must
   ignore them, but the two ends must agree.
4. **Mask staleness.** `iWhichPeptide`/`modNumIdx` numbering is an artifact of one specific
   `.idx` build (protein/peptide iteration order, mod-permutation table construction order).
   Rebuilding the same FASTA with the same params is not guaranteed to reproduce identical
   numbering unless it goes through the exact determinism path T18 already tests for byte-exact
   `.idx` rebuilds -- and even then, the mask is tied to *that* `.idx` file, not to "this FASTA +
   these params" in the abstract. Fingerprinting (Section 4.3) turns a silent mismatch into a
   loud one.
5. **Charge-1-only FI scope, and the phospho-modloss decision expands it.** Carafe predicts
   `b_z2`/`y_z2` (and `*_modloss_*` in phospho mode); none of that is insertable into today's FI
   regardless of intensity, since the FI has no charge-2 or neutral-loss ion class at all --
   `AddFragments()` only ever computes/inserts one `dBion`/`dYion` pair per position, full stop.
   Per the decision to include phospho modloss channels from the start (open question 7,
   resolved), **this is no longer just a filtering feature for phospho mode** -- it requires
   adding a genuinely new ion class (neutral-loss b/y, i.e. `dBion - dNeutralLoss`/
   `dYion - dNeutralLoss` at whichever residues carry a lossy mod) to `AddFragments()`,
   `FragmentPeptidesStruct`-adjacent bookkeeping, and the CSR posting-list build, before any
   Carafe-driven filtering of it is meaningful. Treat this as its own implementation phase
   (Section 6, Phase 2b) with its own correctness testing, separate from and gating the
   modloss-aware mask/threshold logic. Charge-2 b/y remains out of scope for v1 (nothing in the
   modloss decision requires it); z2 still only matters for *normalization* (open question 3).

## 6. Phased implementation plan

- **Phase 0 -- COMPLETE (2026-08-06).** Validation spike, no production code. Hand-verified the
  AlphaBase-row-to-Comet-index remapping (pitfall 2) and the tuple-keying approach (pitfall 1)
  against real data -- both confirmed. Results and evidence in Section 6.1. A real doc bug
  (`-i`/`-j` swapped) was also caught and fixed as a side effect (Section 6.1).
- **Phase 1 -- COMPLETE (2026-08-06).** `idx_to_carafe.py` changes: tuple-identity sidecar
  mapping, dedup-aware fan-out (Section 4.1). Results in Section 6.2.
- **Phase 2a -- COMPLETE (2026-08-06).** Mask builder (general mode only):
  `tools/carafe_ms2_to_fi_mask.py`, `b_z1`/`y_z1`, max-across-charges, tuple-keyed, fingerprinted
  mask file (Section 4.2, 4.3). Results in Section 6.4.
- **Phase 2b -- FI neutral-loss ion class (phospho). Design decided (2026-08-06), not yet
  implemented.** Extend `AddFragments()`/the FI's posting-list build to compute and insert
  `b_modloss`/`y_modloss` ions at lossy-mod-bearing residues, independent of any Carafe
  filtering -- this must exist and be correct on its own (with its own test coverage) before
  the mask builder is extended to cover it in Phase 2c. Rules, decided by replicating Comet's
  existing classic-search neutral-loss mechanism exactly rather than inventing a new one (see
  Section 6.5 for the code-reading that grounded this):
  - Reuse `g_staticParams.variableModParameters.varModList[].dNeutralLoss` (**primary loss
    only** -- `dNeutralLoss2` deferred, since Carafe's phospho mode has only one modloss
    channel per ion type/charge to validate/mask a second FI loss series against). Both values
    are already persisted in the `.idx`'s `VariableMod:` header line and already parsed by
    `idx_to_carafe.py`'s `VarModSlot.nl`/`.nl2` -- no `.idx` format change needed.
  - **Single loss event per fragment**, gated on the *nearest* occurrence of the NL-bearing mod
    from the relevant terminus (first-from-N-term for b-ions, first-from-C-term for y-ions) --
    matching `CometSearch.cpp`'s `iPositionNLB`/`iPositionNLY` logic exactly, not multiplied if
    a fragment contains multiple occurrences of the same lossy mod.
  - **Insert both** the unshifted and the loss-shifted fragment as separate FI entries at an
    eligible position (matching classic search's own two-separate-bins behavior), so Phase 2c's
    masking can independently keep/drop each based on Carafe's separate `b_z1` vs
    `b_modloss_z1` predicted intensities.
  - Variable-mod-only (static mods have no `dNeutralLoss` field at all) -- already consistent
    with the FI's existing variable-mod-centric design.
- **Phase 2c -- mask builder, phospho mode.** Extend Phase 2a's tool to also threshold
  `b_modloss_z1`/`y_modloss_z1` once Phase 2b's ion class exists to filter.
- **Phase 3 -- `CometFragmentIndex.cpp` integration.** Mask loading, the count/fill-pass-
  consistent lookup (Section 4.4), the hardening assertion from Section 7's count/fill
  consistency test.
- **Phase 4 -- `comet.params`/CLI/RTS wrapper plumbing** (Section 4.5).
- **Phase 5 -- testing and benchmarking** (Section 7), then documentation of final measured
  numbers (quality tradeoff at a few thresholds, memory/speed delta) analogous to
  `docs/20260730_PI_reduction.md`.

### 6.1 Phase 0 results (2026-08-06)

**Doc correction found along the way: `-i`/`-j` were backwards throughout this document.**
`Comet.cpp:191-202` shows `-i` sets `create_fragment_index` (FI_DB) and `-j` sets
`create_peptide_index` (PI_DB) -- the opposite of what Sections 3, 6, and 8 originally said.
Fixed in place. Also worth noting for later phases: per `CometSearchManager.cpp:2093-2096`'s
comment, "`-i` and `-j` are now synonyms" for the *build* step since the PI_DB/FI_DB
unification -- both call the same `WritePeptideIndex()` and produce a byte-identical `.idx`.
Which mode a given `.idx` is actually *searched* in is controlled independently by
`index_search_type` in the search-time `comet.params` (0=PI_DB, 1=FI_DB, unset defaults to
FI_DB) -- not by which flag built the file. Section 4.5's plumbing should target
`index_search_type`, not a new build-time flag.

**Pitfall 2 (AlphaBase row remapping): CONFIRMED, both structurally and numerically.**

- Fetched AlphaBase's actual source (`MannLabs/alphabase`, `peptide/mass_calc.py`) rather than
  relying on inference from Carafe's usage pattern. Confirmed directly: row `i`'s `b_mass[i]` =
  sum of the first `i+1` residues; `y_mass[i]` = total peptide mass minus `b_mass[i]` = sum of
  the last `nAA-(i+1)` residues. This is the standard complementary cleavage-site pair, as
  assumed.
- Wrote a standalone scratch script (no external deps, not committed -- see note below)
  replicating both Comet's `AddFragments()` loop and AlphaBase's row convention with real
  monoisotopic masses, for 5 test peptides (`ACDEFGHIKL`, `SAMPLER`, `PEPTIDE`, and the length-2/3
  edge cases `AK`, `MNQ`). Result: **every b-ion at Comet loop index `i` numerically matches
  AlphaBase row `i`'s b column; every y-ion at Comet loop index `i` numerically matches AlphaBase
  row `nAA-2-i`'s y column** (not row `i`) -- confirming the mirrored-row remapping formula
  exactly, including at the length-2/3 edges where the `i>1` indexing gate excludes everything.

**Pitfall 1 (tuple-keying vs. positional keying): CONFIRMED empirically against a real build.**

- Built a small real `.idx` (13 raw peptides from a synthetic S/T/Y-rich fixture, phospho on
  S/T/Y up to 2 sites + a variable N-term mod, `max_variable_mods_in_peptide=2`) -> 250 variants,
  via `comet.exe -i` (per the note above, `-i`/`-j` are build-synonyms -- either flag produces
  the identical unified `.idx`; `-i` was used here matching the existing test suite's
  `-i`="FI_DB"-flavored convention, e.g. `run_tests.py`'s T19/T24).
- Added temporary debug instrumentation directly after
  `g_vFragmentPeptides.push_back(sTmp)` in `CometFragmentIndex.cpp` (env-var-gated, dumping
  `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)` for every variant pushed during the FI's
  count pass), rebuilt, and ran a real FI_DB search against that same `.idx`.
- **First attempt used mismatched search-time params (narrower `digest_mass_range` and
  `max_variable_mods_in_peptide` than the build) and got only 125/250 variants at FI-build
  time** -- a useful reminder, not a bug: search-time `comet.params` bounds (mass range, length
  range) genuinely re-filter `g_vRawPeptides`/mod combinations independently of what's baked

### 6.5 Phase 2b neutral-loss rules: grounded in existing code, not invented (2026-08-06)

Before asking the user how FI neutral-loss ion mass/site rules should work, read how Comet's
*classic* (non-indexed) search already handles fragment-ion neutral loss -- it turned out to
already have a complete, working answer, so the actual question became "replicate this, or do
something different" rather than "design this from scratch."

- **`CometSearch/core/Params.h:161`**: `bUseFragmentNeutralLoss` -- a global toggle,
  auto-set `true` by `CometSearchManager.cpp:1403` if *any* variable-mod slot has a nonzero
  `dNeutralLoss`/`dNeutralLoss2`.
- **`data/comet_phospho.params:37`**: `variable_mod02 = 79.966331 STY 0 2 -1 0 0 97.976896` --
  real-world usage: phospho (79.966331 Da, S/T/Y) with a 97.976896 Da (H3PO4) primary neutral
  loss. `dNeutralLoss2` is an optional *second* loss mass, comma-separated in the same params
  field (`Comet.cpp:601`'s `sscanf(szTmp1, "%lf,%lf", ...)`); phospho's canonical config only
  ever sets the primary one.
- **`CometSearch.cpp:2089-2126`**: `iPositionNLB[x]`/`iPositionNLY[x]` are computed once per
  peptide, per NL-bearing mod slot `x` -- the position of the *first* (scanning from the
  N-terminus) and *first-from-the-C-terminus* occurrence of that mod, respectively. Not "every
  occurrence," not "all occurrences combined" -- just the nearest one from each direction.
- **`CometSearch.cpp:2200-2219`**: for each candidate fragment (`ctLen`, ion series, charge),
  a b-ion gets the NL-shifted mass variant if `ctLen >= iPositionNLB[x]` (the fragment's length
  already reaches the first occurrence); a y-ion analogously via `iPositionNLY[x]`. This adds a
  *second*, separately-binned fragment mass (`dNewMass = dFragMass - dNeutralLoss/charge`)
  alongside the normal one -- both are inserted as independently queryable masses, not a
  replacement. Confirms: single loss event per eligible fragment (the mass shift is applied
  once, not once per occurrence within that fragment), and both series exist simultaneously.
- No equivalent `dNeutralLoss` field exists anywhere in `staticModifications` (`Params.h`) --
  fragment neutral loss is variable-mod-only in Comet today, matching the FI's existing
  variable-mod-centric design (`FRAGINDEX_VMODS` etc.) with no adjustment needed.

This is why Section 8's item 9 (below) could be framed as a confirm-or-diverge choice rather
than an open design question -- and why replicating it was the recommended (and chosen)
answer: it keeps FI-mode and classic-mode neutral-loss behavior consistent for the same
peptide/mod/params, `.idx` already carries the needed `dNeutralLoss`/`dNeutralLoss2` values
with no format change, and Carafe's single `b_modloss`/`y_modloss` channel per charge lines up
exactly with "primary loss only."

## 7. Testing and validation plan

- **Alignment correctness unit test (new, required before anything else lands).** Hand-pick one
  small, unmodified peptide with a known sequence (e.g. reuse an existing `tests/unit/data/`
  fixture peptide). Run it through Carafe, independently compute its b/y ion masses via the same
  formula `AddFragments()` uses, and assert the mask builder's AlphaBase-row-to-Comet-index
  remapping produces the expected `(length, ion_type) -> intensity` assignment. This is the test
  that catches pitfall 2.
- **Count/fill consistency test.** Build a masked FI_DB and assert
  `g_iFragmentIndexOffset[uiMaxFragmentArrayIndex]` (total entry count from the count pass)
  exactly equals the number of entries actually written in the fill pass, and that no
  `s_iWritePos[bin]` write ever exceeds the next bin's offset (an assertion/hardening check
  worth adding to `AddFragments()` itself, not just to a test, given the corruption mode in
  pitfall 4 above).
- **Determinism.** Extend the T18 pattern: two independent masked-FI_DB builds from the same
  PI_DB + mask file must be byte-identical.
- **Quality regression, T23/T24-style.** Compare rank-1 PSM counts at 1% FDR (`tools/qvalue.py`)
  between an unfiltered FI_DB and a masked FI_DB on the same real dataset
  (`--bigdata`/`20130226-comet-tests`), at a few threshold values (10%, 5%, 20%) to characterize
  the sensitivity/size tradeoff -- not just confirm "close enough," since this is the whole
  point of the feature and the acceptable tradeoff is a product decision, not a fixed tolerance.
- **Memory/speed benchmark** (`comet-benchmark` skill): FI_DB memory footprint and search Hz,
  masked vs. unfiltered, on the same dataset used for the `docs/20260730_PI_reduction.md`
  measurement so the two documents' numbers are comparable.
- **Scale/compute-cost measurement for the Carafe step itself.** Running `ai_pred.py` over
  hundreds of millions of variants (a realistic no-enzyme whole-proteome FI_DB) is a real
  up-front cost (GPU/CPU time, intermediate TSV/parquet disk space) that this plan does not yet
  have a number for. Should be measured on `human.small.fasta` first, then extrapolated.

## 8. Design decisions (formerly open questions)

All items below were raised as open questions and have since been decided in discussion with
the user (2026-08-05 and 2026-08-06). Kept as a numbered list rather than folded silently into
the sections above, since the reasoning and rejected alternatives are useful context for
implementation and for revisiting any of them later.

1. **Max intensity per fragment across charges.** A given FI variant (peptide+mods) is
   charge-independent, but Carafe's intensity prediction takes charge as an input feature and
   its output can differ by charge. Predict at each configured precursor charge (e.g. 2 and 3),
   then take the per-fragment **max** intensity across charges before thresholding (Section 4.2,
   step 1) -- one shared, charge-agnostic "best case" spectrum per variant, rather than a
   per-charge union of pass/fail decisions or a single fixed charge.
2. **Unscored peptides fall back to fully unfiltered.** A variant Carafe couldn't score
   (unresolved mod name via `idx_to_carafe.py`'s existing skip logic, or outside Carafe's trained
   mass/length/mod range) keeps its current exhaustive fragment set in the FI -- never drop a
   peptide from the FI entirely just because it couldn't be scored (Section 4.3).
3. **Base peak = the single most intense predicted ion across the full predicted spectrum**, not
   restricted to only the channels the FI can insert -- i.e. `max` over every channel Carafe
   predicts for that variant (`b_z1`,`b_z2`,`y_z1`,`y_z2`, plus `b_modloss_z1/z2`/
   `y_modloss_z1/z2` in phospho mode once Phase 2b lands), the same reference regardless of
   search mode (Section 4.2, step 2). A peptide whose true dominant fragment is charge-2 (or
   modloss) still has its charge-1 b/y ions thresholded against that higher reference, even
   though the dominant ion itself is never written to the FI -- this is intentional: it reflects
   the real spectrum's shape rather than an FI-scope-dependent one.
4. **Minimum-fragment floor: keep the top `FRAGINDEX_CARAFE_MIN_KEPT_PEAKS` most intense
   eligible fragments, default 6**, regardless of the relative-intensity threshold, so a peptide
   with an unusually flat or low-confidence predicted spectrum never loses all its FI fragments.
   Not a fixed b/y split -- top-up pulls from the combined pool of length->=3-eligible b and y
   candidates by intensity, and a variant with fewer than 6 eligible fragments total simply keeps
   all of them (no padding). New named constant in `CometSearch/core/Constants.h`, next to the
   existing `FRAGINDEX_MIN_IONS_SCORE`/`FRAGINDEX_MIN_IONS_REPORT` (Section 4.2, step 4).
5. **Threshold is configurable, not hardcoded** -- a `carafe_ms2_to_fi_mask.py` CLI flag
   (`--min-relative-intensity`, default 0.10), alongside `--min-kept-peaks` for item 4's floor.
   Carafe's raw per-fragment intensity output is the durable artifact of the (expensive) GPU
   inference step; re-sweeping either the threshold or the floor re-reads it directly rather than
   re-running `ai_pred.py` -- needed for the T23/T24-style quality-vs-size comparison in Section 7
   regardless (Section 4.2).
6. **Mask generation is a separate offline Python tool**, not folded into `comet.exe -i`.
   `carafe_ms2_to_fi_mask.py` stays a standalone step reading Carafe's raw prediction output,
   distinct from Carafe's own inference step and from Comet's build CLI -- keeps Comet's C++ side
   free of any Python/Carafe dependency (matching `idx_to_carafe.py`'s existing design) and keeps
   the threshold/floor cheaply re-sweepable (item 5) without rerunning GPU inference.
7. **Phospho modloss channels are in scope now, not deferred.** This expands the feature beyond
   filtering: it requires adding a real neutral-loss b/y ion class to the FI itself (Section 5,
   pitfall 5; Section 6, Phase 2b), which today has none. Planned and tested as its own phase,
   gating the modloss-aware mask/threshold logic on it landing first.
8. **Two-step workflow via PI_DB only** -- `comet.exe -j` (PI_DB) -> `idx_to_carafe.py` ->
   Carafe -> mask -> `comet.exe -i` (masked FI_DB) reading that same PI_DB. No direct
   FASTA-to-masked-FI_DB path is needed; Carafe requires an already-enumerated peptide universe
   to predict against, so a PI_DB intermediate is effectively unavoidable regardless of how the
   CLI is packaged.
9. **Phase 2b's neutral-loss rule replicates Comet's existing classic-search mechanism
   exactly**, rather than inventing a new one -- grounded in reading `CometSearch.cpp`'s
   already-working fragment-NL code (Section 6.5) before asking the user anything: a single
   loss event per eligible fragment, gated on the *nearest* occurrence of the NL-bearing mod
   from the relevant terminus (first-from-N-term for b, first-from-C-term for y). Reuses
   `varModList[].dNeutralLoss`, already persisted in the `.idx` and already parsed by
   `idx_to_carafe.py` -- no format change needed for this decision alone.
10. **Primary neutral loss (`dNeutralLoss`) only for now; `dNeutralLoss2` deferred.** Carafe's
    phospho mode predicts a single `b_modloss`/`y_modloss` channel per ion type/charge, so a
    second FI loss series would have no predicted signal to mask it against.
11. **The FI inserts both the unshifted and the loss-shifted fragment as separate entries** at
    an NL-eligible position (matching classic search's own two-separately-binned-masses
    behavior), so Phase 2c's masking can independently keep/drop each based on Carafe's
    separate `b_z1` vs `b_modloss_z1` predicted intensities, rather than the loss-shifted mass
    replacing the unshifted one.
