## 1. Goal

Today, `CometFragmentIndex::AddFragments()` inserts **every** b/y ion (from ion length 3 up to
`length-1`, singly charged only) of **every** modified-peptide variant into the fragment ion
index (FI). That is exhaustive and mod-agnostic -- it has no notion of which fragments a real
spectrum for that peptide would actually produce.

The goal of the `carafe` branch is to replace that exhaustive population with a **predicted**
one:

1. Export the peptide+mod universe of a built `.idx` (PI_DB) to Carafe via `tools/idx_to_carafe.py`
   (already implemented on this branch).
2. Run Carafe's `ai_pred.py` MS2 model over that universe to predict a relative-intensity
   spectrum (b/y, charge 1 and 2) for every peptide variant.
3. Keep only the peaks at or above some relative-intensity threshold vs. the base peak (user
   specified this as 10% to start).
4. Populate the FI using **only** the kept (predicted, high-intensity) fragments instead of the
   full exhaustive set.

Expected payoff, quantified against real numbers already measured on this codebase
(`docs/20260730_PI_reduction.md`, Section 1): for one real FI_DB build, `g_iFragmentIndex` (the
flat posting-list array) alone was **13.78 GiB out of a 19.0 GB total FI_DB memory footprint** --
by far the largest single structure in the index. Trimming the average number of kept fragments
per peptide directly shrinks that array (memory), and every per-query bin lookup during search
walks a shorter posting list at that fragment mass (speed) -- both benefits scale with however
much the 10%-threshold actually reduces fragment count in practice (measured: Section 6.14 --
~24.9% smaller FI at the default 10% threshold, at a ~94% PSM-recall cost on a moderate-scale
real dataset).

## 2. Relevant existing code (read before implementing)

### 2.1 How the FI is populated today

`CometFragmentIndex::GenerateFragmentIndex()` (`CometSearch/CometFragmentIndex.cpp:169`) runs a
two-pass build over `g_vRawPeptides` (unique unmodified peptides) x every valid mod-variant
(enumerated by `AddFragmentsThreadProc()`/`PermuteIndexPeptideMods()`):

- **Pass 1 (count, `bCountOnly=1`)**: for every `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)`
  variant, `AddFragments()` computes the variant's mass, appends a `FragmentPeptidesStruct` to
  `g_vFragmentPeptides`, and increments a per-mass-bin counter in `g_iFragmentIndexOffset[]` for
  every b/y ion it would insert.
- Between passes, **`g_vFragmentPeptides` is sorted by `dPepMass`** (`CometFragmentIndex.cpp:214`).
  The variant's position in this sorted vector becomes its `iWhichFragmentPeptide` -- the value
  actually written into the FI posting list.
- **Pass 2 (fill, `bCountOnly=0`)**: re-runs `AddFragments()` per (now sorted-index) variant,
  writing `iWhichFragmentPeptide` into `g_iFragmentIndex[]` at each b/y ion's CSR write position.

Inside `AddFragments()` (`CometFragmentIndex.cpp:409`), the ion loop is:

```cpp
for (int i = 0; i < iEndPos; ++i)   // iEndPos = peptide length - 1
{
   dBion += <residue i mass>;               // cumulative -> b-ion of length i+1
   dYion += <residue iEndPos-i mass>;        // cumulative -> y-ion of length i+1
   ...
   if (i > 1)   // *** first two ion lengths (1, 2) are never indexed, at any intensity ***
   {
      // insert dBion into FI (charge 1 only -- no charge-2 b/y ion is ever indexed today)
      // insert dYion into FI (charge 1 only)
   }
}
```

Two things to note for the plan below:

- **Only charge-1 b/y ions exist in the FI at all.** There is no charge-2, no neutral-loss, no
  a-ion. Carafe's `b_z2`/`y_z2`/`*_modloss_*` channels are irrelevant to *what gets inserted*,
  but they do matter to *how the base peak is defined* -- it's the max over all predicted
  channels, not just the insertable ones (Section 8, item 3).
- **Ion lengths 1 and 2 are already unconditionally excluded**, independent of any Carafe
  prediction. The mask only ever needs to cover lengths 3..(peptide length - 1).

### 2.2 Where PI_DB and FI_DB diverge on variant enumeration

`CometPeptideIndex::WritePeptideIndex()` (`CometSearch/CometPeptideIndex.cpp`) persists only the
raw unmodified-peptide table and protein list to the `.idx` -- no per-variant modified-peptide
data is written to disk at all. Both PI_DB and FI_DB regenerate their own modified-peptide
variant enumeration **in memory, fresh every session**, from that raw table plus the active
variable-mod settings (the `.idx`'s own `VariableMod:` header line, per
`docs/20260811_restore_idx_header_mods.md`) -- but via **two separately maintained enumeration
code paths**, not one shared function: PI_DB uses `EnumerateIndexPeptideMods()`
(`CometPeptideIndex.cpp`), sorted by mass; FI_DB uses `AddFragmentsThreadProc()`
(`CometFragmentIndex.cpp`), which independently re-enumerates from the same input tables and
re-sorts by mass itself. `tools/idx_to_carafe.py` gets its variant identity from
`comet.exe -x`'s export of the PI_DB enumeration (`read_exported_variants()`), not by reading
anything off the `.idx` directly (Section 6.10).

Two independent enumeration code paths over the same inputs is the load-bearing fact here: nothing
guarantees they visit variants in the same order, which is exactly why a mask must be keyed by
the content tuple `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)`, never by row position or
enumeration order (Section 4.1, pitfall 1) -- confirmed empirically in Section 6.1.

### 2.3 Carafe's prediction output shape

`ai_pred.py`'s `predict_ms2()` (`Carafe/src/main/resources/py/v2/ai_pred.py:38`) takes a
`sequence`/`mods`/`mod_sites`/`charge` TSV/parquet (exactly `idx_to_carafe.py`'s output schema)
and writes three row-aligned outputs per batch:

- `<prefix>_ms2_df.tsv` -- the input rows echoed back, augmented with `frag_start_idx`/
  `frag_stop_idx` (AlphaBase/peptdeep convention: each precursor occupies `nAA-1` contiguous rows
  in the two files below).
- `<prefix>_ms2_pred.tsv` -- the flat fragment table, columns `b_z1`,`b_z2`,`y_z1`,`y_z2`
  (general mode; phospho mode adds `*_modloss_*`), **relative intensities**, one row per
  cleavage site across all peptides (sliced by `frag_start_idx:frag_stop_idx`).
- `<prefix>_ms2_mz_df.tsv` -- the same shape, but m/z instead of intensity (not needed for this
  project -- Comet already computes its own fragment m/z deterministically and does not need
  Carafe's).

AlphaBase's row `r` (0-indexed, `r = 0 .. nAA-2`) for a peptide of length `nAA` corresponds to
cleavage after residue `r+1`: **`b` column of row `r`** is `b_{r+1}` (length `r+1`), **`y` column
of row `r`** is `y_{nAA-r-1}` (length `nAA-r-1`).

## 3. End-to-end pipeline (as implemented -- see Section 6 for the phase-by-phase build-out)

```
FASTA --(comet.exe -i)--> FI_DB .idx   [the ONE .idx used throughout -- masking only
         |                              ever applies to an FI_DB search]
         v
comet.exe -x  --> variants_export.tsv  [forces a temporary PI_DB-mode read of that
         |                              same FI_DB-tagged .idx, reusing
         |                              EnumerateIndexPeptideMods() rather than
         |                              reimplementing it -- Section 6.10]
         v
tools/idx_to_carafe.py (.idx + variants_export.tsv)
   --> peptide/mods/mod_sites/charge TSV  (one row per FI variant, dedup'd)
   --> variant-map sidecar: row_index -> (iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)
         |
         v
Carafe: ai_pred.py --mode general|phosphorylation --device cpu|cuda
         |
         v
  <prefix>_ms2_df.tsv (frag_start_idx/frag_stop_idx) + <prefix>_ms2_pred.tsv (intensities)
         |
         v
tools/carafe_ms2_to_fi_mask.py
   - per variant: base peak = max over ALL predicted channels (b_z1,b_z2,y_z1,y_z2[,modloss])
   - keep (position, ion_type) where intensity >= threshold * base peak (threshold configurable, default 0.10)
   - top up to FRAGINDEX_CARAFE_MIN_KEPT_PEAKS (default 6) most intense eligible fragments if fewer passed
   - remap AlphaBase row -> Comet ion-length index (b: row i; y: mirror row nAA-2-i)
   - drop ion lengths 1,2 (never indexed anyway)
   - key each variant by (iWhichPeptide, modNumIdx, cNtermMod, cCtermMod) -- NOT row position
         |
         v
   fragment mask file, fingerprinted to the source .idx (CRC-32, Section 8 item 13)
         |
         v
search the SAME FI_DB .idx with fragment_index_predicted_mask_file=<mask> (comet.exe batch,
or RealtimeSearch.exe --mask <mask>, Section 6.13) -- rebuilds the in-memory FI bins filtered
by the mask on every process start (Section 6.13's key finding: the .idx itself is unchanged;
masking happens fresh at FI-build time, every time)
```

Backward compatible by construction: no mask configured -> current exhaustive behavior,
unchanged.

## 4. Component-by-component plan

### 4.1 `tools/idx_to_carafe.py` changes

- Add a stable variant-identity column to the output (or a parallel `.idx`-order sidecar) --
  the natural choice is `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)`, i.e. exactly the
  fields PI_DB's own variant enumeration already identifies each variant by (Section 2.2).
  **Do not** rely on output row order/position as the key (see pitfall 1 below).
- Current default behavior collapses identical `(sequence, mods, mod_sites, charge)` rows from
  different `(iWhichPeptide, modNumIdx, ...)` tuples (`seen` dedup set,
  `tools/idx_to_carafe.py:576`). That is correct for a Carafe *training/prediction* input (no
  reason to predict the same spectrum twice), but the mask-building step needs to fan the
  single prediction back out to every tuple that mapped to it. Either keep dedup and carry a
  `list[tuple]` per unique row, or add a `--no-dedup`-equivalent default specifically for this
  workflow. Recommend: keep dedup for compute efficiency, emit a side mapping file
  (`dedup_key -> [tuples]`) so the mask builder can broadcast one prediction to every tuple that
  shares it.
- Charge column: currently emits 2 rows per variant (`--charges 2,3` default) since
  `idx_to_carafe.py` was written for spectral-library generation, where every precursor charge
  state matters. For *this* use case, b/y ion m/z is charge-independent and only the model's
  intensity output can vary by charge -- keep both configured charges' rows; the mask builder
  takes the per-fragment max across them (Section 8, item 1).

### 4.2 New tool: `tools/carafe_ms2_to_fi_mask.py`

Reads `<prefix>_ms2_df.tsv` (for `frag_start_idx`/`frag_stop_idx` and the tuple-identity column
added in 4.1) + `<prefix>_ms2_pred.tsv` (intensities), and for every variant:

1. Slice its `nAA-1` rows out of `_ms2_pred.tsv`, once per predicted charge state (per the
   decision on open question 1: predict at each configured charge, e.g. 2 and 3, and take the
   **per-fragment max intensity across charges** before thresholding -- `b_z1[r] = max` over
   the configured charges' `b_z1[r]` values, etc.).
2. Compute the base peak: the single most intense value across **every** predicted channel for
   that variant (`b_z1`, `b_z2`, `y_z1`, `y_z2`, plus `b_modloss_z1/z2`/`y_modloss_z1/z2` in
   phospho mode) -- i.e. the true predicted-spectrum base peak, not restricted to whichever
   channels the FI can actually insert (open question 3, decided). A peptide whose real dominant
   fragment is charge-2 will correctly threshold its charge-1 ions against that higher reference,
   even though the charge-2 ion itself is never written to the FI.
3. For each AlphaBase row `r` (0-indexed): candidate-keep `b_{r+1}` if
   `b_z1[r] >= threshold * base_peak` (**only if `r+1 >= 3`**, i.e. skip AlphaBase rows 0,1);
   candidate-keep `y_{nAA-r-1}` similarly from the `y` column of the **mirrored** row (see
   pitfall 2) (only if `nAA-r-1 >= 3`).
4. **Minimum-fragment floor** (open question 4, decided): if fewer than
   `FRAGINDEX_CARAFE_MIN_KEPT_PEAKS` candidate-eligible (length >= 3) fragments cleared the
   threshold in step 3, top-up by intensity (across the combined pool of eligible b and y
   candidates, not a fixed b/y split) until either `FRAGINDEX_CARAFE_MIN_KEPT_PEAKS` are kept or
   every eligible fragment for that variant is kept (whichever comes first -- a variant with
   only 4 eligible fragments total keeps all 4, it does not pad to 6). Named constant lives in
   `CometSearch/core/Constants.h`, alongside the existing `FRAGINDEX_MIN_IONS_SCORE`/
   `FRAGINDEX_MIN_IONS_REPORT` etc. (`CometSearch/core/Params.h:81-82`); default **6**.
5. Pack the per-variant result as two bitmasks (b-kept, y-kept), each up to
   `MAX_PEPTIDE_LEN-1 = 50` bits (`CometSearch/core/Constants.h:24`) -- fits in one `uint64_t`
   each.
6. Write `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod) -> (bMask: u64, yMask: u64)` to a mask
   file, fingerprinted against the source `.idx` (Section 4.3).

**Threshold and floor are both CLI flags** on this tool (`--min-relative-intensity 0.10`,
`--min-kept-peaks 6`, matching the `FRAGINDEX_CARAFE_MIN_KEPT_PEAKS` default), not hardcoded
(open question 5, decided). To make re-sweeping either one cheap, `_ms2_pred.tsv`/
`_ms2_mz_df.tsv` (Carafe's raw per-fragment intensity output) should be treated as the durable
artifact of the expensive GPU inference step -- rerunning `carafe_ms2_to_fi_mask.py` at a new
threshold or floor re-reads those files directly rather than re-invoking `ai_pred.py`.

This is the step that needs a dedicated correctness unit test before it touches real data --
see Section 7.

### 4.3 Mask file format

- New standalone file (not folded into the `.idx` itself -- keeps this experimental feature from
  touching the recently-stabilized unified `.idx` format of `docs/20260730_PI_reduction.md`,
  and lets a mask be regenerated/tuned without rewriting the (large) `.idx`).
- Header: path/hash of the source PI_DB `.idx` (e.g. its `NumPeptides:` count + raw-peptide-table
  byte size, or a full checksum) so a mismatched mask is rejected at load time with a clear error
  rather than silently corrupting the FI build (see pitfall 4). This directly guards against the
  "regenerate the same FASTA into a new `.idx`" trap: `iWhichPeptide`/`modNumIdx` numbering is
  **not** guaranteed stable across independent `.idx` builds, only across *reads of one already-
  built `.idx` file*.
- Body: sorted `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)` -> `(bMask, yMask)` records,
  binary-searchable (or loaded into an `unordered_map`/open-addressed table keyed by a packed
  96-bit tuple) at FI build time.
- A variant with no entry in the mask (peptide skipped by `idx_to_carafe.py`, e.g. unresolved
  mod name, or outside Carafe's trained range) falls back to **fully unfiltered** for that
  variant (open question 2, decided).

### 4.4 `CometFragmentIndex.cpp` integration

- Load the mask (if configured) once, alongside `g_vRawPeptides`/`MOD_SEQS`/`MOD_NUMBERS`, before
  `GenerateFragmentIndex()` runs.
- In `AddFragments()`, right before each of the two `if (dBion > ... && dBion < ...)` /
  `if (dYion > ... && dYion < ...)` insertion blocks (`CometFragmentIndex.cpp:590`/`612`), add a
  mask lookup gated on `i > 1` (matches the existing skip) using the *same* tuple key
  `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)` already available as this function's
  parameters, checking bit `(i - 2)` (or however lengths 3.. get indexed into the 50-bit mask)
  of the b- or y-mask respectively.
- **The count pass and the fill pass must apply byte-identical mask logic.** They already share
  one `AddFragments()` body gated by `bCountOnly`, so as long as the mask check sits *before*
  the `bCountOnly` branch (applies to both), this falls out naturally -- but it is worth an
  explicit code-review note/assertion, since a count/fill mismatch here doesn't crash cleanly;
  it silently overflows or underflows the CSR write-position array, corrupting unrelated mass
  bins. This is the single highest-severity correctness risk in the whole feature and deserves
  its own test (Section 7 / T27, now `t36_predicted_mask_integration` -- Section 6.24).
  **Update (2026-08-24, Section 6.24):** the write-position mechanism this paragraph originally
  described, a single global `s_iWritePos` array plus a `Mutex`, no longer exists --
  master's independent parallelization of `GenerateFragmentIndex()` (merged into `carafe`
  2026-08-23) replaced it with per-thread partitioned write cursors (`AddFragments()` gained
  `pLocalFragPeptides`/`pFillBinCounts`/`pFillWriteCursor` parameters, one of which is non-null
  per call to select count-pass/fill-count-subpass/fill-write-subpass; see
  `CometSearch/CometFragmentIndex.h`'s doc comment on `AddFragments()` for the current
  contract). The correctness risk this paragraph warns about is unchanged in kind -- a count/
  fill divergence still corrupts the index silently rather than crashing -- so the merge
  ported the hardening check (originally comparing `s_iWritePos[bin]` against the CSR sentinel
  after fill) onto the new scheme, comparing the last partition's final write-cursor position
  per bin instead. `t36_predicted_mask_integration` (formerly `t27_predicted_mask_integration`)
  passed unmodified against the merged code, and the full unit suite was re-run clean, but no
  *new* test was added specifically to exercise the parallel count/fill path's mask
  interaction -- masking correctness under the new parallelization is covered only
  incidentally, by T36 continuing to pass, not by a test written to target it.

### 4.5 `comet.params` / CLI / RTS plumbing

- New `comet.params` key, e.g. `fragment_index_predicted_mask_file` (empty = disabled, matching
  the `dFragIndexMinMass`/`iFragIndexSkipReadPrecursors` naming convention already in
  `CometSearch/core/Params.h`).
- Since FI generation is shared between the batch build path and RTS's
  `InitializeSingleSpectrumSearch()` (per `CLAUDE.md`'s threading table, the FI globals are
  "read-only after init" for both), this needs a `SetParam()` call site on the RTS side mirroring
  `index_search_type`'s own precedent. (Phase 4/Section 6.13 found no `CometWrapper` changes were
  actually needed -- `SetParam()` is already fully generic -- and that the live driver to update
  is `RealtimeSearch/SearchMS1MS2.cs`, not `RealtimeSearch/Search.cs`, which is an older example
  file explicitly left untouched; see Section 6.13 for what was actually built.)

## 5. Critical implementation pitfalls (found while reading the existing code)

1. **Positional/row-index keying would be wrong.** FI_DB regenerates `g_vFragmentPeptides`
   independently of PI_DB's own variant enumeration (Section 2.2) via a *different* enumeration
   function, then re-sorts by mass. There is no guarantee this reproduces the exact row order
   `idx_to_carafe.py` gets from `comet.exe -x`'s PI_DB-enumeration export. The mask **must** be
   keyed by the content tuple `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)`, never by a row
   index or position in any exported/predicted file.
2. **AlphaBase row <-> Comet ion index is not a straight 1:1 mapping.** Comet's loop iteration
   `i` produces `b_{i+1}` **and** `y_{i+1}` (same *length*, computed via a forward+backward
   two-pointer sweep) -- not the complementary cleavage-site pair. AlphaBase's row `r` instead
   produces `b_{r+1}` and `y_{nAA-r-1}` (complementary cleavage-site pair, standard convention).
   So Comet's `y_{i+1}` lives in AlphaBase row `nAA-2-i`, not row `i`. Getting this wrong doesn't
   crash -- it silently keeps/drops the wrong y-ions, a purely quality-degrading bug that would
   be very hard to notice without a targeted test.
3. **Only lengths >= 3 are ever indexed** (`i > 1` gate, independent of any mask). Mask bits for
   length 1-2 are meaningless; the mask builder should either omit them or the consumer must
   ignore them, but the two ends must agree.
4. **Mask staleness.** `iWhichPeptide`/`modNumIdx` numbering is an artifact of one specific
   `.idx` build (protein/peptide iteration order, mod-permutation table construction order).
   Rebuilding the same FASTA with the same params is not guaranteed to reproduce identical
   numbering unless it goes through the exact determinism path T18 already tests for byte-exact
   `.idx` rebuilds -- and even then, the mask is tied to *that* `.idx` file, not to "this FASTA +
   these params" in the abstract. Fingerprinting (Section 4.3) turns a silent mismatch into a
   loud one.
5. **Charge-1-only FI scope, and the phospho-modloss decision expands it.** Carafe predicts
   `b_z2`/`y_z2` (and `*_modloss_*` in phospho mode); none of that is insertable into today's FI
   regardless of intensity, since the FI has no charge-2 or neutral-loss ion class at all --
   `AddFragments()` only ever computes/inserts one `dBion`/`dYion` pair per position, full stop.
   Per the decision to include phospho modloss channels from the start (open question 7,
   resolved), **this is no longer just a filtering feature for phospho mode** -- it requires
   adding a genuinely new ion class (neutral-loss b/y, i.e. `dBion - dNeutralLoss`/
   `dYion - dNeutralLoss` at whichever residues carry a lossy mod) to `AddFragments()`,
   `FragmentPeptidesStruct`-adjacent bookkeeping, and the CSR posting-list build, before any
   Carafe-driven filtering of it is meaningful. Treat this as its own implementation phase
   (Section 6, Phase 2b) with its own correctness testing, separate from and gating the
   modloss-aware mask/threshold logic. Charge-2 b/y remains out of scope for v1 (nothing in the
   modloss decision requires it); z2 still only matters for *normalization* (open question 3).

## 6. Phased implementation plan

- **Phase 0 -- COMPLETE (2026-08-06).** Validation spike, no production code. Hand-verified the
  AlphaBase-row-to-Comet-index remapping (pitfall 2) and the tuple-keying approach (pitfall 1)
  against real data -- both confirmed. Results and evidence in Section 6.1. A real doc bug
  (`-i`/`-j` swapped) was also caught and fixed as a side effect (Section 6.1).
- **Phase 1 -- COMPLETE (2026-08-06).** `idx_to_carafe.py` changes: tuple-identity sidecar
  mapping, dedup-aware fan-out (Section 4.1). Results in Section 6.2.
- **Phase 2a -- COMPLETE (2026-08-06).** Mask builder (general mode only):
  `tools/carafe_ms2_to_fi_mask.py`, `b_z1`/`y_z1`, max-across-charges, tuple-keyed, fingerprinted
  mask file (Section 4.2, 4.3). Results in Section 6.4.
- **Phase 2b -- COMPLETE (2026-08-06).** FI neutral-loss ion class (phospho): extended
  `AddFragments()` to compute and insert `b_modloss`/`y_modloss` ions at lossy-mod-bearing
  residues, independent of any Carafe filtering -- this must exist and be correct on its own
  (with its own test coverage) before the mask builder is extended to cover it in Phase 2c.
  **Also found and fixed a serious pre-existing, unrelated bug** in the same function while
  implementing this -- see Section 6.6 for both. Rules, decided by replicating Comet's
  existing classic-search neutral-loss mechanism exactly rather than inventing a new one (see
  Section 6.5 for the code-reading that grounded this):
  - Reuse `g_staticParams.variableModParameters.varModList[].dNeutralLoss` (**primary loss
    only** -- `dNeutralLoss2` deferred, since Carafe's phospho mode has only one modloss
    channel per ion type/charge to validate/mask a second FI loss series against). Both values
    are already persisted in the `.idx`'s `VariableMod:` header line and already parsed by
    `idx_to_carafe.py`'s `VarModSlot.nl`/`.nl2` -- no `.idx` format change needed.
  - **Single loss event per fragment**, gated on the *nearest* occurrence of the NL-bearing mod
    from the relevant terminus (first-from-N-term for b-ions, first-from-C-term for y-ions) --
    matching `CometSearch.cpp`'s `iPositionNLB`/`iPositionNLY` logic exactly, not multiplied if
    a fragment contains multiple occurrences of the same lossy mod.
  - **Insert both** the unshifted and the loss-shifted fragment as separate FI entries at an
    eligible position (matching classic search's own two-separate-bins behavior), so Phase 2c's
    masking can independently keep/drop each based on Carafe's separate `b_z1` vs
    `b_modloss_z1` predicted intensities.
  - Variable-mod-only (static mods have no `dNeutralLoss` field at all) -- already consistent
    with the FI's existing variable-mod-centric design.

### 6.5 Phase 2b neutral-loss rules: grounded in existing code, not invented (2026-08-06)

Before asking the user how FI neutral-loss ion mass/site rules should work, read how Comet's
*classic* (non-indexed) search already handles fragment-ion neutral loss -- it turned out to
already have a complete, working answer, so the actual question became "replicate this, or do
something different" rather than "design this from scratch."

- **`CometSearch/core/Params.h:161`**: `bUseFragmentNeutralLoss` -- a global toggle,
  auto-set `true` by `CometSearchManager.cpp:1403` if *any* variable-mod slot has a nonzero
  `dNeutralLoss`/`dNeutralLoss2`.
- **`data/comet_phospho.params:37`**: `variable_mod02 = 79.966331 STY 0 2 -1 0 0 97.976896` --
  real-world usage: phospho (79.966331 Da, S/T/Y) with a 97.976896 Da (H3PO4) primary neutral
  loss. `dNeutralLoss2` is an optional *second* loss mass, comma-separated in the same params
  field (`Comet.cpp:601`'s `sscanf(szTmp1, "%lf,%lf", ...)`); phospho's canonical config only
  ever sets the primary one.
- **`CometSearch.cpp:2089-2126`**: `iPositionNLB[x]`/`iPositionNLY[x]` are computed once per
  peptide, per NL-bearing mod slot `x` -- the position of the *first* (scanning from the
  N-terminus) and *first-from-the-C-terminus* occurrence of that mod, respectively. Not "every
  occurrence," not "all occurrences combined" -- just the nearest one from each direction.
- **`CometSearch.cpp:2200-2219`**: for each candidate fragment (`ctLen`, ion series, charge),
  a b-ion gets the NL-shifted mass variant if `ctLen >= iPositionNLB[x]` (the fragment's length
  already reaches the first occurrence); a y-ion analogously via `iPositionNLY[x]`. This adds a
  *second*, separately-binned fragment mass (`dNewMass = dFragMass - dNeutralLoss/charge`)
  alongside the normal one -- both are inserted as independently queryable masses, not a
  replacement. Confirms: single loss event per eligible fragment (the mass shift is applied
  once, not once per occurrence within that fragment), and both series exist simultaneously.
- No equivalent `dNeutralLoss` field exists anywhere in `staticModifications` (`Params.h`) --
  fragment neutral loss is variable-mod-only in Comet today, matching the FI's existing
  variable-mod-centric design (`FRAGINDEX_VMODS` etc.) with no adjustment needed.

This is why Section 8's item 9 (below) could be framed as a confirm-or-diverge choice rather
than an open design question -- and why replicating it was the recommended (and chosen)
answer: it keeps FI-mode and classic-mode neutral-loss behavior consistent for the same
peptide/mod/params, `.idx` already carries the needed `dNeutralLoss`/`dNeutralLoss2` values
with no format change, and Carafe's single `b_modloss`/`y_modloss` channel per charge lines up
exactly with "primary loss only."

### 6.6 Phase 2b results, including a serious pre-existing bug found and fixed (2026-08-06)

**Implementation** (`CometFragmentIndex.cpp`'s `AddFragments()`): computes, per variant,
`iPositionNLB[slot]`/`iPositionNLY[slot]` (one entry per real variable-mod slot,
`FRAGINDEX_VMODS`-sized) incrementally during the *same* forward+backward ladder sweep the
function already runs -- not a separate pre-pass, unlike classic search's own
residue-position-based `iPositionNLB`/`iPositionNLY`. Verified this simplification is
semantically identical to the classic-search algorithm, first algebraically (b: ladder index
`i` directly *is* the eligibility threshold, since the b-walk's `sPeptide[i]` match happens
exactly at residue position `i`; y: same, since the y-walk's "first encountered in loop order"
directly corresponds to "nearest occurrence from C-term" -- the mirrored-row derivation from
Section 6.1 doesn't recur here, this is a different index space), then empirically against a
direct Python translation of classic search's original algorithm across 10 hand-picked cases
(mod at every edge position, two occurrences of the same lossy mod, two different lossy mod
types simultaneously, a non-lossy mod, very short peptides) -- all 10 matched exactly before
any C++ was written.

At each `i > 1` ladder position, for every real variable-mod slot with a nonzero
`dNeutralLoss` whose nearest-occurrence position has been reached, both an NL-shifted b-ion
and an NL-shifted y-ion are inserted as separate FI entries (Section 8 item 11), using the
same bounds-check/`BIN()`/overflow-guard pattern as the existing unshifted insertions, and
gated identically in both the count and fill passes (the single highest-severity risk flagged
in Section 4.4/5) since the check sits before the `bCountOnly` branch, exactly like the
existing code it sits alongside.

**A serious pre-existing bug was found (not introduced by this change) while validating
end-to-end**, in two stages:

1. Built a real phospho FI_DB (`ACDEFGSK`, phospho-S, matching `data/comet_phospho.params`'
   `97.976896` Da neutral loss) with NL enabled vs. disabled and compared FI entry counts --
   expected a difference, got none (20 vs. 20). Debug tracing found `AddFragments()`'s
   `varModList[mods[j] - 1]` (its *existing* line, immediately above where the new NL code was
   added) was reading `varModList[-1]` -- undefined behavior, empirically `dVarModMass=0.0` in
   this build -- because `mods[j]` was `0`, not `1`. Every variable-mod-modified b/y ion
   fragment in the FI has been computed **as if unmodified** for as long as this code has
   existed; the peptide's *precursor* mass (a separate, correctly-written loop three lines
   above) was unaffected, so existing tests (T19 included) still found the right peptide via
   its unmodified-region fragments plus correct precursor mass -- they never checked that the
   *modified* fragment's own mass was right.
2. Fixing the naive `mods[j] - 1` -> `mods[j]` was **still wrong** in general (only happened to
   work in every test case run so far, since they all had the active variable-mod slot at
   index 0 with no gap before it). Cross-referencing `CometPeptideIndex.cpp`'s independently-
   hardened `MaterializeOneEntry()` (the PI_DB-mode equivalent) showed the real rule:
   `mods[j]`/`mods[k]` are indices into a *compacted* active-slot list
   (`CometPeptideIndex::GetVModSlotForAllModsIdx()`, built by scanning slots
   `0..FRAGINDEX_VMODS-1` and keeping only the active ones) -- not raw `varModList` indices at
   all, and not simply off by one. `mods[j]` only equals the real slot when every active
   `variable_modNN` among the first `FRAGINDEX_VMODS` is contiguous from slot 0 (the common
   case, including every fixture/config used in this project so far -- which is exactly why
   this had gone unnoticed). A config with a gap (e.g. `variable_mod01` left unset while
   `variable_mod02` carries a real mod) would have silently applied the *wrong* modification's
   mass to modified fragment ions.

**Full fix**: added `#include "CometPeptideIndex.h"` to `CometFragmentIndex.cpp` (no circular-
include issue -- `CometPeptideIndex.h` already includes `CometFragmentIndex.h`, and this is a
`.cpp`-to-`.h` include, not header-to-header), fetched
`CometPeptideIndex::GetVModSlotForAllModsIdx()` once per `AddFragments()` call, and routed
*every* `mods[]` lookup in the function -- the pre-existing precursor-mass loop and the

### 6.8 Wider sweep for the same bug class (2026-08-06)

After three independent instances of the same bug turned up one at a time (Sections 6.6, 6.7),
did a systematic sweep instead of waiting for a fourth to surface by accident: every consumer
of `MOD_NUMBERS[...].modifications[]` (the compacted-index array) across `CometSearch/`, found
via `grep -rn "MOD_NUMBERS\.at(\|MOD_NUMBERS\[" CometSearch/*.cpp` (to find every place the
array is obtained) cross-referenced against `grep -n "mods\["` per file (to find every place a
local `mods` alias is actually dereferenced) -- six total consumer sites, no other local
variable name is used for this array anywhere in the codebase:

| Site | File:function | Status |
|---|---|---|
| Precursor-mass loop | `CometFragmentIndex.cpp` `AddFragments()` | Fixed, Section 6.6 |
| Fragment-ladder loop (b and y) | `CometFragmentIndex.cpp` `AddFragments()` | Fixed, Section 6.6 |
| `piVarModSites` reconstruction | `CometSearch.cpp` `SearchFragmentIndex()` | Fixed, Section 6.7 |
| `tryPush` mass accumulation | `CometPeptideIndex.cpp` `EnumerateIndexPeptideMods()` | Already correct |
| Protein-mod-filter check | `CometPeptideIndex.cpp` `EnumerateIndexPeptideMods()` | Already correct |
| `pcVarModSites`/mass reconstruction | `CometPeptideIndex.cpp` `MaterializeOneEntry()` | Already correct |
| **Protein-mod-filter check** | **`CometFragmentIndex.cpp` `AddFragmentsThreadProc()`** | **Fixed here, new** |

`CometPeptideIndex.cpp`'s three sites (the PI_DB path) were already correct throughout --
including a comment at line 461 explicitly documenting the `mods[i] == -1` guard requirement.
`CometFragmentIndex.cpp`/`CometSearch.cpp` (the FI_DB path) had three bugs out of four sites,
reinforcing that this is a real, recurring pattern in the FI_DB code specifically, not one
isolated typo.

**The fourth bug**, `CometFragmentIndex.cpp`'s `AddFragmentsThreadProc()` (a different function
from `AddFragments()` -- the per-raw-peptide driver loop that calls `AddFragments()` once per
valid mod combination), had a protein-variable-mod-filter check with *two* problems, found by
diffing it against `CometPeptideIndex.cpp`'s correct equivalent:

```cpp
// before (both bugs):
if (!cometbitcheck(g_vRawPeptides.at(iWhichPeptide).siVarModProteinFilter, mods[i]))

// after:
if (mods[i] != -1
   && !cometbitcheck(g_vRawPeptides.at(iWhichPeptide).siVarModProteinFilter,
                      vModSlotForAllModsIdx.at((size_t)mods[i])))
```

1. Missing the `mods[i] != -1` guard every other consumer of this array has -- `mods[i] == -1`
   means "not modified at this candidate position in this specific combination", and
   `cometbitcheck()`'s `(byte) & (1 << nbit)` is undefined behavior for a negative `nbit`.
2. The same compacted-vs-real-slot confusion as the other three sites, here misusing the
   compacted index as a bit position into `siVarModProteinFilter` (confirmed real-slot-indexed
   by cross-referencing this same function's own `ctNtermMod`/`ctCtermMod` checks a few lines
   above, and by `CometSearch.cpp:2685-2724`'s filter-construction code, which sets bits via
   `iWhichMod - 1`, a raw slot).

Fixed the same way as the other three sites (fetch `GetVModSlotForAllModsIdx()` once, translate
before use).

**Important nuance, unlike the other three fixes: this one is currently unreachable dead code
in the documented build-then-search workflow.** Attempted the same empirical validation
approach (a peptide with two candidate mod-acceptor residues and `max_variable_mods_in_peptide
= 1`, so every combination leaves one candidate position unselected -- guaranteed to hit
`mods[i] == -1` -- searched against a prebuilt `.idx` with `protein_modslist_file` configured)
and found **no behavior difference between the buggy and fixed code**. Added a one-line debug
print to check directly: `bVarModProteinFilter` is `0` (false) at this point in the standard
"build `.idx`, then search it" flow that every test in this repo (and the documented workflow)
uses. Root cause: `CometSearchManager.cpp:2020`'s
`ReadProteinVarModFilterFile()` call -- the only place that ever sets `bVarModProteinFilter =
true` at search time -- is explicitly gated `if (bCreateFragmentIndex || iDbType ==
DbType::FASTA_DB)`, with the comment "Do this here only for classic search or if creating the
plain peptide index." For FI_DB search against a prebuilt `.idx`, `bCreateFragmentIndex` is
`false` and `iDbType` is `FI_DB`, so that condition never holds; `AddFragmentsThreadProc()`
(reached via `search/FiStrategy.cpp`'s `sqSearch.CreateFragmentIndex(tp, false)`, called
unconditionally, not gated on `bCreateFragmentIndex`) always runs with the protein filter
switched off. Since the PI_DB/FI_DB build unification, `.idx` construction itself goes through
`CometPeptideIndex.cpp`'s `EnumerateIndexPeptideMods()` (already correct), not
`AddFragmentsThreadProc()` at all -- so there is currently no supported path that reaches this
buggy code with `bVarModProteinFilter` actually true. Fixed anyway (matches
`CometPeptideIndex.cpp`'s already-correct equivalent exactly, and CLAUDE.md's code-review
checklist explicitly calls out unreachable-but-wrong branches as worth flagging even when
currently harmless), but **no regression test was added for this specific fix** -- there is no
current way to exercise it end-to-end to prove one meaningful, unlike T25's proven-meaningful
gap-config test for the other three sites. Worth revisiting if a future change reopens a path
to `AddFragmentsThreadProc()` with the protein filter active.

Full suite re-run after this fix: 41/41 pass (unchanged from Section 6.7, as expected for a
currently-unreachable code path).

### 6.9 Phase 2c results, and a newly-discovered blocker for real-data validation (2026-08-10)

`tools/carafe_ms2_to_fi_mask.py` now supports phospho-mode modloss channels alongside Phase
2a's general-mode masking, implementing Section 4.2 exactly (auto-detects mode from
`ms2_pred.tsv`'s header -- no new CLI flag, per Section 8 item 6's minimal-surface intent):

- `read_ms2_pred()` normalizes every fragment row to a fixed 8-tuple (`CHANNELS` order) and
  returns `has_modloss` alongside it; a file with only *some* of the four modloss columns
  raises rather than silently guessing.
- `max_across_charges()` and the base-peak computation generalized from hardcoded 4-field
  logic to loop over all 8 channels -- base peak is unconditionally "max over everything in
  `merged_rows`", **not gated on `has_modloss`**, matching Section 8 item 3's "the same
  reference regardless of search mode" exactly (in real usage this is moot: a general-mode
  `ms2_pred.tsv` never has nonzero modloss values in the first place, since
  `read_ms2_pred()` zero-pads those columns when they're absent).
- **New Phase 2c design decision** (not pre-covered by Section 8's existing 11 items, which
  predate modloss channels entering this tool's scope): the modloss b/y pool gets its own
  independent threshold+floor pass, using the *same* `--min-relative-intensity`/
  `--min-kept-peaks` values as the unshifted pool (no new flags) but never mixing candidates
  between the two pools -- matches item 11's "independently keep/drop each" and keeps the two
  ion classes symmetric.
- **Skip rule for the modloss pool**, to avoid computing (and floor-padding) a pool with no
  real signal: skipped entirely when either (a) the input has no modloss columns at all
  (general mode), or (b) the variant is unmodified (`modNumIdx == -1`). (b) is not just an
  optimization -- `CometFragmentIndex.cpp`'s `bFragmentNL` gate
  (`bUseFragmentNeutralLoss && modNumIdx >= 0`) means an unmodified variant can *never* get an
  NL-shifted FI entry regardless of what any mask says, so a computed modloss mask for one
  would be dead weight, and worse, the floor would force meaningless zero-intensity picks into
  the mask file for it. A modified-but-non-lossy variant (e.g. oxidation only) is deliberately
  NOT special-cased beyond this: Carafe's own modloss prediction is expected to already read
  near-zero for such variants (ad hoc testing during this session confirmed non-eligible-
  fragment modloss channels predict exactly `0.0`), so the threshold alone should naturally
  exclude them; the floor could still force a few zero-intensity entries in, which is harmless
  dead data since `CometFragmentIndex.cpp`'s own `iPositionNLB`/`iPositionNLY` eligibility gate
  (a property of the peptide's actual mod combination) will never consult those mask bits for
  a variant with no lossy mod slot active.
- **Bit-index convention carries over unchanged**: confirmed from `CometFragmentIndex.cpp`
  directly (not assumed) that the neutral-loss-shifted-variant insertion runs inside the *same*
  `for (int i = 0; i < iEndPos; ++i)` loop, at the same `i`, immediately after the unshifted
  insertion (`CometFragmentIndex.cpp:693-732`, both gated by the same `if (i > 1)`) -- so
  `bModlossMask`/`yModlossMask` need no separate remap from `bMask`/`yMask`'s.
- **Mask file format bumped to v2** (`ENTRY_FMT` gained `bModlossMask`/`yModlossMask`, two more
  `u64` fields; `MASK_FILE_MAGIC` bumped from `v1` to `v2` so a mismatched reader fails loudly
  rather than misinterpreting byte offsets). `GeneralMode` header field is now genuinely
  derived from `has_modloss` rather than hardcoded to `1`.

**Validated with a dedicated unit test suite** (`tests/unit/test_carafe_ms2_to_fi_mask.py`,
pure Python, no `comet.exe`/Carafe/`.idx` dependency -- per Section 4.2's "this is the step

### 6.10 Fixing the .idx v1->v2 blocker: comet.exe -x, and re-fixing idx_to_carafe.py (2026-08-10)

Section 6.9 found that `idx_to_carafe.py` can no longer read the peptide-mod-variant
enumeration off disk at all -- Phase 0.5 stopped persisting `MOD_NUMBERS`/`MOD_SEQS`/the
compact variant array in the `.idx` file entirely. Two implementation options were considered:
reimplement `CometPeptideIndex::EnumerateIndexPeptideMods()`'s combinatorics a second time in
Python (reading `comet.params` directly), or have Comet itself export its own canonical
enumeration. **Chose the latter**: a from-scratch Python reimplementation of a genuinely
nontrivial, correctness-critical C++ combinatorics engine (`ModificationsPermuter::
getModifiableSequences()`/`getModificationCombinations()`'s bitmask generation, plus
`EnumerateIndexPeptideMods()`'s ~150 lines of nested mod-number/terminal-mod/protein-filter/
mass-range logic) would need to be re-derived and re-verified every time that C++ changes --
exactly the wrong place to accept ongoing drift risk for a mapping the mask file's entire
validity depends on. Exporting instead makes the numbering match *by construction* (same code,
same `.idx`, same `comet.params`, run twice) rather than by hoping two independent
implementations stay in lockstep.

**New Comet CLI flag `-x<file>`** (`Comet.cpp`, `CometInterfaces.h`/`CometSearchManager.h`/`.cpp`,
`CometPeptideIndex.h`/`.cpp`): `CometSearchManager::ExportPeptideIndexVariants()` runs a
narrow path deliberately separate from `DoSearch()`'s full pipeline (no thread pool, no
spectra input, no strategy/writer dispatch -- mirrors how `-p`/`-q`'s `PrintParams()` already
short-circuits before `DoSearch()` in `Comet.cpp`) -- `InitializeStaticParams()` ->
`ValidateSequenceDatabaseFile()` -> force `iDbType = DbType::PI_DB` (this export has no FI_DB
analog) -> `CometPeptideIndex::ReadPeptideIndex()` (which internally builds `MOD_NUMBERS`/
`MOD_SEQS`/`g_vDBIndexVariants` fresh from live `comet.params`, same as any real PI_DB
session) -> `CometPeptideIndex::ExportVariants()`, new: for each `g_vDBIndexVariants` entry,
calls the *existing* `MaterializeOneEntry()` (previously only used at query time to
reconstruct a candidate's `pcVarModSites`) and writes `iWhichPeptide/modNumIdx/cNtermMod/
cCtermMod/mass/sequence/sites` as a TSV, `sites` being a semicolon-separated `pos:mass` list
(`pos` matching `VarModSites::position`'s own convention: 0-based residue index, or
`len(sequence)`/`len(sequence)+1` for n-term/c-term) -- zero new combinatorics code, reusing
the same reconstruction logic a live search already trusts.

**A real bug was found and fixed while validating this end to end**: the export's first test
run against a real phospho `.idx` produced only the unmodified baseline variant -- the
phospho-modified variant was silently missing. Root cause: every other entry point that
reaches `EnumerateIndexPeptideMods()` (`DoSearch()`, `InitializeSingleSpectrumSearch()`)
explicitly sets `g_massRange.dMinMass`/`dMaxMass` from `comet.params`' `digest_mass_range`
itself; `ExportPeptideIndexVariants()`'s narrower path didn't call this, leaving both at their
zero-initialized default. `EnumerateIndexPeptideMods()`'s `tryPush` lambda rejects any
candidate whose mass falls outside `[dMinMass, dMaxMass]` -- with both at `0.0`, every
variable-mod-modified candidate's mass (always `> 0`) failed this check and was silently
dropped, while the always-included unmodified baseline (`GenerateVariantArray()`'s first loop
has no mass check at all) survived regardless -- so the bug produced a *plausible-looking*
single-row output instead of an obvious failure. Fixed by adding the same two-line
`g_massRange` initialization `DoSearch()`/`InitializeSingleSpectrumSearch()` already do.
Caught by exactly the kind of empirical, real-data validation this section's tooling exists
to do -- not by code review -- and now covered by `t26_export_peptide_index_variants`'s
row-count assertion so it can't silently regress. A **full clean rebuild** (`make clean &&
make`) was needed at one point during this work to clear an unrelated stale-incremental-build
artifact (`T19`/`T20`'s AScore score read back as `0.0` after an incremental `make` following
the `ICometInterfaces.h` virtual-method addition; a clean rebuild fixed it immediately, and
the *same* incremental build had already produced a correct `libcometsearch.a` for the actual
new code paths exercised here -- worth remembering as a "when in doubt, `make clean`" gotcha
for future header-interface changes, not a code bug in this session's work).

**`idx_to_carafe.py` re-fixed** to consume this new export instead of the removed on-disk
sections: `IdxReader` now checks for the `"Comet index database v2"` magic and a two-pointer
footer (`clPeptidesFilePos`/`clProteinsFilePos` -- the old v1 format's `perm_pos`/`var_pos`
are simply gone; the protein list is now the last section, running to `footer_pos`), and no
longer parses `VariableMod:` (removed from the header) or the permutation-table/compact-
variant-array sections (removed from the file). `decode_variable_mods()` -- the previous
from-scratch reimplementation of `MOD_NUMBERS`/`MOD_SEQS`/`slot_map` decoding -- is deleted
outright rather than adapted, since `read_exported_variants()`'s new `ExportedVariant.var_sites`
already arrives fully decoded as `(pos, mass)` pairs from the canonical C++ source;
`build_mods_mod_sites()` only needed `slot.mass` -> `mass` since the tuple shape changed.
Added a defensive cross-check (`variant.sequence != raw.seq`) so a `-x` export accidentally
paired with the wrong `.idx` fails loudly instead of silently annotating the wrong peptide's
mods -- mirrors `carafe_ms2_to_fi_mask.py`'s own `.idx`-fingerprint guard in spirit, cheap to
add since the export already carries the sequence for free.

**`carafe_ms2_to_fi_mask.py`'s `idx_fingerprint()`** also referenced the now-gone `var_pos`;
fixed to fingerprint `[pep_pos, footer_pos)` (raw peptide table + protein list -- everything
the v2 format still persists) instead of `[pep_pos, var_pos)`. Documented, not silently
patched over, an important consequence of Phase 0.5 this raises: the fingerprint now only
proves *`.idx` compatibility* (`iWhichPeptide` numbering, raw peptide content) -- it can no
longer prove *`modNumIdx` compatibility*, since that now also depends on whichever
`comet.params` variable mods were live when `-x` produced the export a mask's tuples were
built from. A mask built against this exact `.idx` but a *different* `comet.params` would
still pass the fingerprint check while carrying stale/meaningless `modNumIdx` keys. **This is
a new, previously-nonexistent risk Phase 3 needs its own guard for** -- e.g. verifying a
looked-up mask entry's tuple still resolves to the same sequence it's about to mask (mirroring
`idx_to_carafe.py`'s new sequence cross-check above), rather than trusting the `.idx`
fingerprint alone to mean "this mask still applies."

### 6.11 Phase 3: CometFragmentIndex.cpp mask integration (2026-08-10)

**New class `CometPredictedMask`** (`CometSearch/CometPredictedMask.h`/`.cpp`), loaded once from
`CometFragmentIndex::CreateFragmentIndex()` (right after `ReadPeptideIndex()`, before
`GenerateFragmentIndex()`) via the new `fragment_index_predicted_mask_file` `comet.params` key
(Section 4.5; empty = disabled, matching `sCompoundModsFile`'s convention exactly):

- Reads the v3 mask format (`tools/carafe_ms2_to_fi_mask.py`'s `write_mask_file()`), keeps
  entries sorted by `(iWhichPeptide, modNumIdx, cNtermMod, cCtermMod)`, and answers `Lookup()`
  via binary search -- Section 4.3's primary suggestion, chosen over a hash map since
  `AddFragments()` only needs one lookup per *variant* (cached in locals, not per fragment --
  see below), so `O(log n)` per variant is negligible next to the `O(peptide length)` work each
  variant's ladder sweep already does.
- **`.idx` fingerprint switched from SHA-256 to CRC-32** (mask format bumped v2->v3): Phase 3
  needed to compute the identical fingerprint on both the Python (mask-build) and C++
  (mask-load) sides, and zlib's `crc32()` is already a linked dependency of Comet's C++ build
  (`MSToolkit/extern/zlib-1.2.11`) that Python's `zlib` module wraps bit-for-bit identically --
  matching a hand-written/vendored SHA-256 implementation across two independent languages
  would have been new correctness-critical code for a check that only needs to catch
  accidental mismatches, not resist tampering.
- **Closes Section 6.10's flagged gap**: a new `VarModConfig` header field (serializing the
  first `FRAGINDEX_VMODS` `varModList[]` slots' mass/chars/n-c-term-flags/neutral-loss into one
  comparable string, `CometPredictedMask::ComputeVarModConfigString()`) is written by
  `comet.exe -x` as a `"# VarModConfig: ..."` comment line (the live session that defines
  `modNumIdx` numbering is the only place that can produce it), propagated verbatim through
  `tools/idx_to_carafe.py`'s variant-map sidecar into `tools/carafe_ms2_to_fi_mask.py`'s mask
  header, and compared against the *live* `comet.params`' variable mods at `Load()` time.
  A mismatch is rejected loudly (search fails, clear error naming both configs) rather than
  silently trusted -- closing exactly the gap the `.idx` fingerprint alone couldn't: proving
  `iWhichPeptide` numbering is safe says nothing about whether `modNumIdx` still means the same
  modification. Both the fingerprint mismatch and the `VarModConfig` mismatch paths are
  regression-tested (see below).
- **`AddFragments()` integration**: the four insertion classes (b/y unshifted at
  `CometFragmentIndex.cpp:693`/`711`, b/y modloss inside the NL-shifted loop at `:766`/`:786`)
  each gained a `(maskX & maskBit)` condition folded into their existing `if` guard -- *before*
  the `if (bCountOnly) ... else ...` branch, so the count pass and fill pass see byte-identical
  logic by construction (Section 4.4's explicit requirement; a count/fill mismatch here
  wouldn't crash cleanly, it would silently overflow the CSR write-position array). The mask
  lookup itself happens ONCE per `AddFragments()` call (the tuple key is constant for the whole
  variant), not once per fragment -- this function runs potentially hundreds of millions of
  times for a whole-proteome build, so a per-fragment lookup would multiply that by peptide
  length for no benefit. `Lookup()` "not found" defaults all four masks to all-bits-set
  (fully unfiltered, Section 8 item 2) so the bit-test code path never needs an "is masking
  active for this variant" branch -- disabled, not-found, and found-and-fully-open all run the
  identical code.
- **Count/fill consistency hardening check**, added to `GenerateFragmentIndex()` itself (not
  just a test, per Section 7's explicit ask): after the fill pass, verifies
  `s_iWritePos[bin] == g_iFragmentIndexOffset[bin + 1]` for every bin -- proving the fill pass
  wrote exactly as many entries into each bin as the count pass reserved, no overflow into the
  next bin's territory and no gap. `O(bins)`, negligible next to the `O(peptides)` fill pass it
  follows; catches a count/fill divergence from any future cause, not just masking.

**A real test-setup bug, not a product bug, cost real debugging time**: the first attempt to
validate end-to-end showed a masked build reporting the *same* FI entry count as unmasked --

the test params file had the key appended after `[COMET_ENZYME_INFO]`, and Comet's params
parser silently ignores `key = value` lines in that section (they're read as enzyme table rows

programmatically so this can't recur silently in the test itself.

### 6.12 Merging master's .idx self-description restoration into carafe (2026-08-11)

An unrelated master-branch change landed and was merged into `carafe`
(`docs/20260811_restore_idx_header_mods.md`; PR #125): `.idx` files are self-describing again
-- variable/static mods, enzyme, mass/length range, and decoy mode are all baked into the
header text at build time and override whatever `comet.params` says at search time. The
`.idx` header format bumped v2 (Section 6.9/6.10's version) to v4 (`IndexSearchType:` restored,
then `MaxVariableModsInPeptide:`/per-slot `iMaxNumVarModAAPerMod` added), and the `-i`/`-j`
CLI flags stopped being pure build-time synonyms: each now permanently locks the resulting
`.idx`'s `IndexSearchType:` (FI_DB/PI_DB) rather than leaving that decision to the search-time
`index_search_type` param.

This directly touches Sections 6.10/6.11 and design decisions 12-14 above, which were written
against the intervening Phase-0.5-only world where the `.idx` carried no mod information at
all and `comet.params` was the *only* source of truth for variable mods at every step
(build, `-x` export, and search alike). Those sections are left as-written -- they're an
accurate record of that phase -- but two of their conclusions no longer describe current
behavior and are corrected here rather than silently rewritten in place:

- **Section 6.10/decision 12's "mods don't matter when building the PI_DB, comet.params at
  `-x` time is what decides them" framing is now backwards.** As of this merge,
  `CometPeptideIndex::ReadPeptideIndex()` overwrites live `g_staticParams.variableModParameters`
  from the `.idx`'s own header the moment it runs -- which happens at the *start* of both the
  `-j`/`-i` build step and the `-x` export step. So the variable mods a `-x` export actually
  reflects are whichever ones were live when the `.idx` was **built**, not whatever
  `comet.params` is passed to `-x` itself (that file's mod settings are read, then immediately
  discarded). Rebuilding with different mods is cheap (Section 6.1/`docs/20260730_PI_reduction.md`),
  so this doesn't reopen any workflow blocker -- it just means step 1 (`-j`), not step 2 (`-x`),
  is now where mod choice happens. `tools/idx_to_carafe.py`'s module docstring and argparse help
  text, and `tools/carafe_ms2_to_fi_mask.py`'s `idx_fingerprint()` docstring, were updated to
  match.
- **Decision 14's `VarModConfig` guard is still needed, but for a narrower reason.** It no
  longer catches "mask built against different `comet.params` than is live at search time" --
  that scenario can't happen any more, since `comet.params`' variable-mod settings are ignored
  at both `-x` and search time alike. What it still catches: the raw peptide/protein table an
  `.idx` fingerprint covers can be byte-identical across two builds of the same FASTA that used
  *different* variable mods (e.g. rerunning `-j` over the same output filename after editing
  `comet.params`, then reusing an older mask/export pair) -- in that case the fingerprint alone
  would still pass while `modNumIdx` numbering had silently changed underneath it. The
  mechanism (`CometPredictedMask::Load()` comparing the mask's embedded `VarModConfig` string
  against live `g_staticParams.variableModParameters`) and its regression tests are unchanged --
  only the narrative of *what drift it's protecting against* needed correcting.

No functional/behavioral code changes were needed for either point -- both are documentation-
only fixes to comments/docstrings in `tools/idx_to_carafe.py` and `tools/carafe_ms2_to_fi_mask.py`.
Verified via the merge's own full clean-rebuild pass (Linux 45/45, Windows 45/45; see
`docs/20260811_restore_idx_header_mods.md` for the merge itself) -- no further test run was
needed for this comment-only follow-up.

### 6.13 Phase 4: RTS/CometWrapper plumbing (2026-08-11)

**Scoping finding: no `CometWrapper`/native-side code changes were needed at all.**
`fragment_index_predicted_mask_file` already flows through the fully generic,
string-keyed `SetParam`/`GetParamValue` param store (`CometSearchManager::_mapStaticParams`)
every other `comet.params` key uses -- confirmed by checking `compoundmods_file`
(`sCompoundModsFile`), which works identically with zero per-key wrapper code anywhere in
`CometWrapper.h`/`.cpp`. `CometSearchManagerWrapper::SetParam(String^, String^, String^)`
forwards to `CometSearchManager::SetParam()` generically, with no per-key allow-list on either
side of the C++/CLI boundary.

**A second, more consequential finding corrected this doc's own assumption about when the
mask needs to be supplied.** Sections 6.10-6.12 (and the original Phase 4 bullet above, before
this section) implicitly framed the mask as something that only matters once, when generating
a `.idx` -- consistent with how variable mods/enzyme/decoy settings work post-
`docs/20260811_restore_idx_header_mods.md` (baked into the header, read back automatically
forever after). **The fragment-ion index does not work that way**: `CometFragmentIndex::
CreateFragmentIndex()` -- the same function `CometPredictedMask::Load()` is wired into --
only ever builds the in-memory CSR bin structure (`g_iFragmentIndex`/`g_iFragmentIndexOffset`)
fresh from the `.idx`'s persisted raw-peptide table (`g_vRawPeptides`); there is no
`WriteFragmentIndex()`/`ReadFragmentIndex()` counterpart that persists the *bins themselves* to
disk. This function runs on **every process start** that opens an FI_DB `.idx` -- batch
`comet.exe` search, `comet.exe -i` build, and RTS's `CometSearchManager::
InitializeSingleSpectrumSearch()` all call it identically (confirmed by reading
`InitializeSingleSpectrumSearch()`: `sqSearch.CreateFragmentIndex(tp, true)` runs
unconditionally after `ReadPeptideIndex()`, not gated on `bCreateFragmentIndex`). So
`fragment_index_predicted_mask_file` must be set on *every* search invocation that should
apply the mask, not just the one that originally built the `.idx` -- confirmed against the
user directly before implementing, since it inverts this doc's earlier framing.

  via `SetParam("fragment_index_predicted_mask_file", ...)` unconditionally near the top of

  branch that gates the enzyme/mod/mass-range settings -- those only matter the one time a
  missing `.idx` gets auto-built; the mask, per the finding above, matters every time. Empty
  string (the default) is a no-op on the native side regardless of PI_DB/FI_DB mode.

  (non-zero exit) rather than merely report a wrong count.
- Item 3's "two independent masked-FI_DB builds ... byte-identical" is what T27 already does, in
  the only form that's actually meaningful here: since `CreateFragmentIndex()` rebuilds the FI

  persisting them to a masked `.idx`, there is no serialized masked-FI_DB file for a T18-style
  byte-compare -- process-level determinism (two independent `comet.exe` invocations against the
  same `.idx`+mask) is the correct granularity, and T27's `"masked run 2"` sub-test already
  asserts identical FI-entry counts and PSM rows across two such invocations.

Confirmed by re-running both: `t26_export_peptide_index_variants` and
`t27_predicted_mask_integration` -- 2/2 passed, 0 failed.

### 6.16 Critical bug found post-hoc: Carafe row-order corruption, and the fix (2026-08-12/13)

**How this was found.** A 10-17% PSM loss at 1% FDR (Sections 6.14/6.15) is significant enough
to demand a root cause, not just an accepted cost -- the request was to isolate the highest-
E-value unmasked PSMs missing from the masked runs and confirm there's no implementation error.
Chasing why specific high-confidence PSMs were dropped led to checking Carafe's own echoed input
(`<prefix>_ms2_df.tsv`) against `idx_to_carafe.py`'s `out_tsv` at the same row position -- and
finding they didn't match. Systematic random sampling (not just the one anecdotal case) found
**0 of 8** row-position matches at the full 7,130,366-row scale, **0 of 6** at Section 6.14's
197,782-row scale, and **0 of 6** at its 92,741-row scale.

**Root cause, confirmed in Carafe's own source** (`models.py`'s `ModelInterface.predict()`,
the base class both the MS2 and RT models share):

```python
def predict(self, precursor_df: pd.DataFrame, *, batch_size=1024, verbose=False, **kwargs):
    if 'nAA' not in precursor_df.columns:
        precursor_df['nAA'] = precursor_df.sequence.str.len()
        precursor_df.sort_values('nAA', inplace=True)
        precursor_df.reset_index(drop=True, inplace=True)
```

`ai_pred.py` reads `out_tsv` once into a dataframe `a`, passes `a` by reference into
`model_mgr.predict_ms2(a, ...)`, and later writes that **same object** back out as
`_ms2_df.tsv`. Since `a` lacks an `nAA` column on input, the `inplace=True` sort above silently
reorders `a` (and drops its original index) as a side effect of prediction -- so the file Carafe
echoes back is sorted by peptide length, not in `out_tsv`'s original row order. This is why the
bug was invisible at small scale: Phase 0's original 250-row spike (Section 6.1) only ever
checked row 0, which a stable sort trivially leaves in place regardless of how badly everything
after it got shuffled.

**Impact.** `tools/carafe_ms2_to_fi_mask.py`'s `read_ms2_df()` assumed `_ms2_df.tsv`'s Nth data
row was `out_tsv`'s Nth row (`ms2_df[row_index]`, a positional lookup) -- silently wrong at every
real scale this project has run. Because the corrupting sort key is peptide length (`nAA`), the
practical effect is that each variant's predicted fragment intensities usually got swapped with
those of a **different peptide of the same length** -- not random noise, but confidently wrong
data with no signal in the mask file itself (correct headers, correct entry count, plausible-
looking masks) that anything was amiss.

**Fix 1 -- join by content, not position.** `idx_to_carafe.py`'s own dedup step already
guarantees `(sequence, mods, mod_sites, charge)` is unique across `out_tsv` (confirmed
empirically: 0 collisions at the full 7,130,366-row scale), and Carafe echoes those four columns
verbatim in `_ms2_df.tsv` alongside the `nAA`/`frag_start_idx`/`frag_stop_idx` columns it adds --
so joining on that tuple instead of file position is correct regardless of whatever internal
reordering `ai_pred.py` does. `carafe_ms2_to_fi_mask.py` changes:
- New `read_out_tsv()`: `out_tsv` row_index -> `(sequence, mods, mod_sites, charge)`.
- `read_ms2_df()` rewritten: now returns `(sequence, mods, mod_sites, charge)` ->
  `(nAA, frag_start_idx, frag_stop_idx)`, keyed by content; raises if a duplicate tuple appears
  (would mean the file wasn't produced from the paired `out_tsv`, or the two desynced).
- `out_tsv` added as a new required positional CLI argument (the script previously only took
  `idx_file`, `variant_map_tsv`, `ms2_df_tsv`, `ms2_pred_tsv`, `out_mask_file` -- it never read
  `out_tsv` itself before, only its `.variants.tsv` sidecar).
- Module docstring's false "row-aligned... Carafe preserves row order end-to-end" claim (which
  Section 6.3 believed it had empirically confirmed, at the 250-row scale that happens to survive
  a stable sort) replaced with a "Row-order correctness" section explaining the real mechanism.

**Fix 2 -- memory, surfaced while re-running the corrected script at real scale.** The original
`read_ms2_pred()` stored all ~87M fragment rows of the real oxmet `ms2_pred.tsv` as a Python list
of 8-tuples of Python floats -- roughly 300+ bytes/row in pure object/container overhead, ~28GB
for this run alone. Against a 31GB machine, this swap-thrashed to a near-standstill (observed:
11 CPU-seconds of real progress across 10 wall-clock minutes, with swap usage climbing the whole
time) -- bad enough that the first corrected-script run was killed rather than left to
(possibly never) finish. Replaced with `FragmentTable`, a small class storing one
`array.array('d')` per channel instead of a list of tuples -- same double precision, no numeric
behavior change, ~64 bytes/row instead of 300+ (~5x reduction) -- while keeping the exact same
external interface (`table[start:stop]` still returns a list of tuples, built on demand only for
the slice asked for). The corrected rebuild then completed cleanly, no swapping, in 8m50s.

**Regression test.** `test_content_join_survives_ms2_df_reordering`
(`tests/unit/test_carafe_ms2_to_fi_mask.py`) builds a 2-peptide `out_tsv` and a deliberately-
reversed-order `_ms2_df.tsv` (mirroring the real length-based reordering, using two different-
length peptides), and confirms the content join recovers the correct
`(nAA, frag_start_idx, frag_stop_idx)` for each `out_tsv` row_index despite the file-order
mismatch -- plus a duplicate-tuple case, confirming it raises rather than silently
picking one. All 8 unit tests in that file pass (7 pre-existing + this one).

**Empirical impact**, measured by rebuilding the real oxmet 10% mask (Section 6.15's own data)
with the fixed script against the same already-completed real Carafe output -- no Carafe
re-run needed, since the bug is entirely downstream of Carafe's own (correct, just reordered)
predictions:

| | Old (buggy) mask | Fixed mask |
|---|---|---|
| Variant masks written | 3,565,183 | 3,565,183 (same set -- the bug doesn't change *which* variants get masked, only what each one's mask contains) |
| Masks identical between builds | -- | 41,645 (**1.2%**) |
| Masks that differ | -- | 3,523,538 (**98.8%**) |
| Total kept-fragment bits (sum of popcount, all masks) | 44,360,513 | 41,037,305 (-7.5%) |

98.8% of individual variant fragment-keep decisions changed. This was not a rare edge case --
it corrupted nearly every masked variant's kept/dropped fragment choice, in a way that produced
plausible-looking output at every stage (right file sizes, right entry counts, right-shaped
masks) with no internal signal that anything had desynced.

**What this invalidates.** Every prior real-Carafe-run PSM-quality number in this document
(Section 6.14's moderate-scale run, Section 6.15's full-proteome oxmet run, and the charge-2-only
vs. charge-2+3 comparison discussed but not yet written into this doc) was built from a mask
whose per-variant fragment selections were effectively decorrelated from the actual peptide being
masked. **Not affected**: the masked-search mechanics, FI integration (Phase 3), and mask file
format itself -- this was purely an error in *which* predicted intensities got attributed to
*which* peptide during mask construction, upstream of everything Phase 3 onward does with the
resulting mask file. The specific PSM-retention percentages and space-savings figures already
reported (94.4%, 90.4%, 83.1%, etc.) should be treated as **unreliable pending re-validation**
with the corrected pipeline -- not necessarily wrong in direction (masking still prunes the FI
and still costs some PSMs), but not trustworthy as exact figures. See the caveat notes added to
the top of Sections 6.14 and 6.15.

### 6.19 Extending masking to decoys, charge 2+3 and charge-2-only (2026-08-13)

Every run through Section 6.18 uses `idx_to_carafe.py`'s default, which excludes decoys from
Carafe's input entirely -- matching production (Carafe is never asked to predict decoy spectra
for real), but with a direct consequence for these space-savings numbers: `human.canonical.
target-decoy.oxmet.fasta.idx` has an exactly 1:1 target:decoy protein ratio (20,454:20,454), so
a mask that only ever covers targets leaves the other, decoy half of the database's FI entries
completely unfiltered, falling back to Section 8 item 2's "no mask entry -> fully unfiltered"
behavior. That predicts overall database-wide reduction should land at roughly *half* of the
target-only reduction (~27-30%), i.e. ~50-55% database-wide, if decoys were masked too. Tested
here with `idx_to_carafe.py --include-decoys` (charges 2,3 and charges 2 only), otherwise
identical pipeline to Sections 6.17/6.18: same `.idx`, same real spectra
(`20170103_HelaQC_01.mzXML`), same 10% threshold.

Carafe inference over the ~7.1M-row (charge-2-only) / ~14.3M-row (charge 2+3) target+decoy
population took 1h34m and (per Section 6.17-adjacent chat notes) ~3h05m respectively -- both
CPU-only, `~/.carafe/.venv`, no `--threads` override. Mask build required switching
`FragmentTable`'s internal storage from `array.array('d')` to `array.array('f')` (float32) after
the first target+decoy attempt entered real swap-thrashing at ~31GB (the target-only population's
~87M rows had comfortably fit in float64; target+decoy's ~174M rows did not) -- verified safe by
rebuilding the already-validated target-only mask with the new float32 code and diffing it
byte-for-byte against the existing float64-built mask (100% identical, 0 differences across
3,565,183 entries), on the reasoning that 10%-relative-intensity thresholding doesn't need
float64 precision. Both target+decoy masks that follow were built with this float32 fix.

### 6.20 Two more memory/cost fixes ahead of the real human-phospho run (2026-08-14)

Section 6.19's target+decoy runs (~7-14M rows) were still well short of a real full-proteome
*phospho* population -- STY-phospho + M-ox, length 7-50, no enzyme restriction -- which turned
out to enumerate **124,863,304** peptide-mod variants (`phospho_noNL_export.log`: 4.659e6 plain
peptides, 4.242e6 modifiable, 1.249e8 modified), roughly 3x the ~41.75M-row full-proteome figure
Section 6.14's own extrapolation was built from. Two separate memory ceilings turned out to bite
at this new scale, on `idx_to_carafe.py`'s conversion step this time rather than
`carafe_ms2_to_fi_mask.py`'s mask build (Section 6.16's `FragmentTable`/float32 fix already
covers the latter, including this run's own ~2x-larger population -- no further change needed
there).

**Fix 1 -- `idx_to_carafe.py`'s dedup dict, `dedup_key()`.** `main()`'s `seen` dict, used to
collapse duplicate `(sequence, mods, mod_sites, charge)` tuples so repeated variants share one
output row, was keyed on the raw 4-tuple itself. At this run's real scale that tuple -- two
freshly-rendered mod-description strings plus the tuple wrapper's own per-entry Python object
overhead -- costs an estimated ~268 bytes/entry, extrapolating to ~33GB against this box's 31GB
WSL memory ceiling (the underlying Windows host has 64GB; the WSL VM itself is capped at 31GB).
Fixed two ways: (1) `sys.intern()` on the rendered `mods`/`mod_sites` strings before they become
dict values -- free, since `mods_str` especially has low cardinality (bounded by the
combinatorics of a handful of mod names across `max_variable_mods_in_peptide` slots), so without
interning, millions of rows each allocate their own copy of what's really one of a few hundred
distinct strings; (2) replacing the dict *key* itself with `dedup_key()`, a single 128-bit
BLAKE2b hash (`hashlib.blake2b(digest_size=16)`) of the same four fields, null-byte-separated,
returned as a plain Python int. That cuts the key to ~114 bytes/entry (~14.2GB at this run's
scale) independent of string-content repetition, which `sys.intern()` alone can't guarantee
(`mod_sites_str`'s cardinality is data-dependent and less certain than `mods_str`'s).

Not Python's built-in `hash()`: that's only 64 bits, a real birthday-bound collision risk at
~125M entries (p ~ n²/2⁶⁵ ~ 2e-4, roughly 1-in-5000 odds of *any* collision across a full run),
and is randomized per-process by default (`PYTHONHASHSEED`) -- which would silently break this
project's established byte-exact determinism guarantees (the T18-style rebuild comparisons) even
before considering collisions. BLAKE2b at 128 bits puts the same birthday-bound calculation at
p ~ n²/2¹²⁹ ~ 4e-19 -- for comparison, a single machine's undetected-cosmic-ray-bit-flip rate
over the same wall-clock runtime is many orders of magnitude higher than this. A collision here
would silently merge two *different* variants onto one output row (silent data corruption, not a
crash), so this was treated as a correctness-critical choice, not a performance-only one.

**Verification status, stated plainly.** `dedup_key()`'s own correctness (determinism, 128-bit
range, content-not-identity equality, field-boundary non-ambiguity, empty-string handling) is
covered by a dedicated unit test, `tests/unit/test_idx_to_carafe_dedup_key.py` -- confirmed
passing as of this writing (6/6). What this section does *not* have is a saved artifact of a
real-scale before/after comparison (re-running the old raw-tuple-key conversion against the same
real oxMet charge2+3+decoys population and diffing the output row-for-row against the new
`dedup_key()`-based conversion), despite the code's own comments referring to exactly that kind
of check. Forensic evidence from this run's own logs is suggestive but not conclusive: two
earlier attempts at converting this exact `phospho_charge2_withNL` population
(`phospho_charge2_withNL_conversion.log`, started 2026-08-14T02:48Z, and
`_conversion_v2.log`, started 15:44Z) both stop at an identical 226 bytes -- right after printing
the mod-table header, before any row-write progress -- while the third attempt
(`_conversion_v3.log`, started 15:54Z, only 9 minutes after v2) completed cleanly, writing the
full 124,863,304 rows. `idx_to_carafe.py`'s current mtime (08:34Z) falls between v1 and v2, so
v1 plausibly failed under the pre-fix raw-tuple key while v2 and v3 both ran against the
already-fixed code -- which does not cleanly explain why v2 *also* failed identically to v1.
Given this environment's independently-observed filesystem/resource flakiness elsewhere in this
same project (see the chat-session notes on `/mnt/c` write-durability and DrvFs ghost directory
entries), a transient machine-level cause for v2's failure is at least as plausible as a
residual code issue -- but this is not resolved either way. Treat the real-scale verification as
outstanding, not as done: a clean re-run of the byte-for-byte comparison this section's own code
comments claim would close it.

**Fix 2 -- `carafe_ms2_to_fi_mask.py --ignore-modloss`.** A phospho analysis wants both a "with
neutral loss" and a "without neutral loss" mask/search comparison (exactly this run's
`phospho_charge2_withNL`/`phospho_charge2_noNL` pair). Running Carafe's expensive
`--mode phosphorylation` inference twice -- once for real, once just to get a
general-mode-shaped prediction of the *identical* peptide population -- is pure waste: the
modloss channels are simply unused input for a "without NL" mask, not a different prediction.
`--ignore-modloss` makes `carafe_ms2_to_fi_mask.py` treat a phospho-mode `ms2_pred_tsv` as if it
were general-mode output: `base_peak`/threshold computed from the 4 unshifted channels only,
modloss masks always 0, `GeneralMode: 1` in the output header -- byte-for-byte what a real
`--mode general` Carafe run against the same peptides would produce. One Carafe inference run
therefore feeds two `carafe_ms2_to_fi_mask.py` invocations (one plain, one with
`--ignore-modloss`) instead of two full Carafe runs.

A real bug was caught building this: the first version excluded modloss values from the modloss
*pool* but not from the `base_peak` reference itself, so a genuinely high-intensity modloss
prediction could still inflate (or deflate) the threshold used for the *unshifted* masks --
making the "ignore" incomplete and the resulting mask not actually general-mode-equivalent. Fixed
by gating `base_peak`'s own `max()` on the same effective-has-modloss flag; regression-tested by
`test_ignore_modloss_excludes_modloss_from_base_peak` with a fixture where a modloss value (1.00)
strictly dominates every unshifted value (max 0.50) -- proving `base_peak`, and therefore which
unshifted ions clear the threshold, visibly differs between "respect modloss" and
"`--ignore-modloss`" on the same input. Full suite (`tests/unit/test_carafe_ms2_to_fi_mask.py`)
confirmed passing as of this writing (9/9).

**Important companion requirement, not solved by the flag alone.** `CometFragmentIndex.cpp`'s
`bUseFragmentNeutralLoss` is baked into a `.idx`'s own header from its variable-mod config's
neutral-loss field at *build* time (`ParsePeptideIndexHeader()`,
`docs/20260811_restore_idx_header_mods.md`), and `CometPredictedMask::Load()`'s `VarModConfig`
check (which includes `dNeutralLoss` per slot) hard-rejects a mask whose embedded `VarModConfig`
doesn't match the live search's. So a genuine "without NL" *search* still needs its own `.idx`
build (same mod residues/mass/max-per-mod, `neutral_loss` field zeroed) and its own
`comet.exe -x` / `idx_to_carafe.py` export -- for the matching `VarModConfig` string -- even
though the peptide/`modNumIdx` enumeration and the Carafe predictions themselves are identical
between the two. Only the `.idx` build and export are cheap enough (minutes, not hours) to
duplicate; Carafe inference is not, hence the flag.

**This run's actual state as of this writing** matches that design exactly, confirmed from the
working directory rather than assumed: `phospho_withNL.idx` and `phospho_noNL.idx` are both
real, separately-built `.idx` files (`neutral_loss = 97.976896` and `0.0` respectively); both
were exported (`phospho_withNL_export.log` / `phospho_noNL_export.log`) and converted
(`phospho_charge2_withNL_conversion_v3.log` / `phospho_charge2_noNL_conversion.log`) to
byte-identical row counts (124,863,304 each) -- confirming the "identical peptide population"
claim above is actually true for this data, not just true by design. What has *not* happened yet
is any `phospho_charge2_noNL_carafe.*` inference run -- no such file exists under
`20260420-human-phosho/`. That means the currently-running `phospho_charge2_withNL_carafe`
production job (started 2026-08-14, see this session's chat log for its own diagnosis/restart
history) should be the *only* full Carafe inference pass this comparison needs: once it
completes, the "without NL" mask should come from running
`carafe_ms2_to_fi_mask.py --ignore-modloss` against that same run's predictions paired with
`phospho_noNL.idx`'s own variant map -- not from a second multi-hour-to-multi-day Carafe run
against `phospho_charge2_noNL_carafe_peptides.tsv`. Worth confirming explicitly before spending
the compute on a redundant second inference pass.

Findings:

1. **Masking improves PSM yield at 1% FDR in all four pairings** -- not "retains", improves

### 6.23 M1-M6: an ahead-of-time pipeline and the compact prediction store (`.cps`) (2026-08-22)

Section 6.22's validation used masks built by hand-orchestrating each stage; at real
full-proteome-phospho scale the raw Carafe prediction output (`_ms2_df.tsv`/`_ms2_pred.tsv`,
Section 4.2) is 386-395GB, making it impractical to keep around just so a mask threshold
could be re-swept later, and impractical to build a mask from directly in one pass (a
single-pass `carafe_ms2_to_fi_mask.py` run against the full fragment table needs ~116GB of
RAM for the in-memory `FragmentTable`, against a 54GB machine). `docs/
20260822_carafe_prerun.md` designs and implements the fix, in milestones M1-M6; this entry
summarizes what's relevant to this design doc's own narrative -- see that document for the
full plan, every milestone's measurements, and the parquet-vs-TSV/u8-vs-u16 rebuild-diff
experiments that justified the choices below.

**The compact prediction store (`.cps`, `tools/carafe_cps.py`, milestone M2).** A new binary
format that keeps only what mask-building actually consumes from a completed Carafe run --
not the full per-fragment-position table -- at ~35-45x smaller (u8 quantization) than the raw
TSVs it replaces. Per `idx_to_carafe.py` output-row (keyed by that row's 0-based index, the
same key `idx_to_carafe.py`'s variant-map sidecar uses -- Section 4.1):

- `nAA` (peptide length)
- two float32 base-peak references: the max intensity across all 8 predicted channels (the
  with-modloss threshold reference) and the max across the first 4 channels only (the
  `--ignore-modloss`/general-mode reference -- kept separately because it's not
  recomputable from what's stored below, which omits `b_z2`/`y_z2`)
- per cleavage site (`nAA-1` of them, AlphaBase row order): the 4 channels the mask
  candidate-selection logic (Section 4.2) actually thresholds -- `b_z1`, `y_z1`,
  `b_modloss_z1`, `y_modloss_z1` -- quantized relative to the 8-channel base peak as `u8` or
  `u16` (declared in the file header; every stored value is <= that base peak by
  construction, so quantization never saturates)

File layout (little-endian): magic line `b"Comet Carafe CPS v1\n"`; `Key: Value` ASCII header
lines (`SourceOutTsvRows`, `SourceOutTsvHeadCRC32` -- a cheap mispairing guard, not a full
hash -- `Quant` [`u8`|`u16`], `Mode` [`phospho`|`general`]) terminated by a blank line; a
`u64` row count; a directory of `u64` absolute file offsets, one per row; then the per-row
binary payloads themselves (`nAA(u8) base8(f32) base4(f32)` followed by `(nAA-1)` rows of 4
quantized channel values). Quantization: `q = round(v / base8 * QMAX)` clamped to
`[0, QMAX]`; dequantized as `q / QMAX * base8` (`base8 == 0.0` stores, and dequantizes to,
all-zero).

Two properties worth noting for anyone extending this later:

- **The store is `.idx`-flavor-neutral.** Because it's keyed by output-row index over the
  shared peptide population rather than by `.idx`-specific `(iWhichPeptide, modNumIdx, ...)`
  tuples, one store built from a withNL Carafe run can serve *both* the withNL mask build and
  (via `--ignore-modloss`) a noNL mask build for the same population -- Section 6.22's own
  noNL/withNL pair could, if rebuilt today, share one store instead of needing two separate
  Carafe runs.
- **It stores intensities, not a keep/drop decision.** The actual thresholding (Section 4.2's
  `--min-relative-intensity`/`--min-kept-peaks` logic) is applied later, at mask-*build* time
  (`tools/carafe_cps_to_fi_mask.py`, milestone M3, reusing `carafe_ms2_to_fi_mask.py`'s
  threshold/floor/pack helpers exactly so a store-built mask is bit-identical to the TSV path
  modulo quantization) -- not baked into the store itself. This is what makes re-sweeping the
  threshold cheap (~24 minutes at full scale, vs. re-running Carafe): the store retains the
  actual signal, and only the final threshold/floor comparison is redone.

**The rest of the pipeline** (`tools/carafe_pred_to_cps.py` translates a completed
`run_carafe_chunked.sh` run into a `.cps`, M2; `tools/carafe_cps_to_fi_mask.py` builds a
`.fi_mask` from one, M3; `tools/carafe_prerun.sh` drives the whole thing -- idx build, `-x`
export, `idx_to_carafe.py` convert, chunked Carafe inference, `.cps` build, mask build -- as
one resumable command, M4; a `--parquet` transient-output mode for the chunked-inference step
cuts per-chunk disk use ~8x with verified byte-identical downstream stores, M5-M6) is
described fully in `docs/20260822_carafe_prerun.md`; this design doc does not duplicate that
detail. `tests/unit/run_tests.py`'s `t38_carafe_python_suites` (formerly `t29_carafe_python_
suites` -- see Section 6.24) wires the four pure-Python test suites for these tools
(`test_carafe_ms2_to_fi_mask.py`, `test_carafe_alignment.py`, `test_idx_to_carafe_dedup_key.py`,
`test_carafe_cps.py`) into the default test run.

Repo state: `tools/carafe_cps.py`, `tools/carafe_pred_to_cps.py`, `tools/carafe_cps_to_fi_mask.py`,
`tools/carafe_prerun.sh` (new); `tools/run_carafe_chunked.sh` (parquet mode added); no
`CometSearch`/C++ changes (the mask *file format* consumed by `CometPredictedMask::Load()` is
unchanged -- these tools only change how a `.fi_mask` gets built, not what one means).

## 7. Testing and validation plan

- **Alignment correctness unit test (new, required before anything else lands).** Hand-pick one
  small, unmodified peptide with a known sequence (e.g. reuse an existing `tests/unit/data/`
  fixture peptide). Run it through Carafe, independently compute its b/y ion masses via the same
  formula `AddFragments()` uses, and assert the mask builder's AlphaBase-row-to-Comet-index
  remapping produces the expected `(length, ion_type) -> intensity` assignment. This is the test
  that catches pitfall 2.
- **Count/fill consistency test.** Build a masked FI_DB and assert
  `g_iFragmentIndexOffset[uiMaxFragmentArrayIndex]` (total entry count from the count pass)
  exactly equals the number of entries actually written in the fill pass, and that no
  `s_iWritePos[bin]` write ever exceeds the next bin's offset (an assertion/hardening check
  worth adding to `AddFragments()` itself, not just to a test, given the corruption mode in
  pitfall 4 above).
- **Determinism.** Extend the T18 pattern: two independent masked-FI_DB builds from the same
  PI_DB + mask file must be byte-identical.
- **Quality regression, T23/T24-style.** Compare rank-1 PSM counts at 1% FDR (`tools/qvalue.py`)
  between an unfiltered FI_DB and a masked FI_DB on the same real dataset
  (`--bigdata`/`20130226-comet-tests`), at a few threshold values (10%, 5%, 20%) to characterize
  the sensitivity/size tradeoff -- not just confirm "close enough," since this is the whole
  point of the feature and the acceptable tradeoff is a product decision, not a fixed tolerance.
- **Memory/speed benchmark** (`comet-benchmark` skill): FI_DB memory footprint and search Hz,
  masked vs. unfiltered, on the same dataset used for the `docs/20260730_PI_reduction.md`
  measurement so the two documents' numbers are comparable.
- **Scale/compute-cost measurement for the Carafe step itself.** Running `ai_pred.py` over
  hundreds of millions of variants (a realistic no-enzyme whole-proteome FI_DB) is a real
  up-front cost (GPU/CPU time, intermediate TSV/parquet disk space) that this plan does not yet
  have a number for. Should be measured on `human.small.fasta` first, then extrapolated.

## 8. Design decisions (formerly open questions)

All items below were raised as open questions and have since been decided in discussion with
the user (2026-08-05 and 2026-08-06). Kept as a numbered list rather than folded silently into
the sections above, since the reasoning and rejected alternatives are useful context for
implementation and for revisiting any of them later.

1. **Max intensity per fragment across charges.** A given FI variant (peptide+mods) is
   charge-independent, but Carafe's intensity prediction takes charge as an input feature and
   its output can differ by charge. Predict at each configured precursor charge (e.g. 2 and 3),
   then take the per-fragment **max** intensity across charges before thresholding (Section 4.2,
   step 1) -- one shared, charge-agnostic "best case" spectrum per variant, rather than a
   per-charge union of pass/fail decisions or a single fixed charge.
2. **Unscored peptides fall back to fully unfiltered.** A variant Carafe couldn't score
   (unresolved mod name via `idx_to_carafe.py`'s existing skip logic, or outside Carafe's trained
   mass/length/mod range) keeps its current exhaustive fragment set in the FI -- never drop a
   peptide from the FI entirely just because it couldn't be scored (Section 4.3).
3. **Base peak = the single most intense predicted ion across the full predicted spectrum**, not
   restricted to only the channels the FI can insert -- i.e. `max` over every channel Carafe
   predicts for that variant (`b_z1`,`b_z2`,`y_z1`,`y_z2`, plus `b_modloss_z1/z2`/
   `y_modloss_z1/z2` in phospho mode once Phase 2b lands), the same reference regardless of
   search mode (Section 4.2, step 2). A peptide whose true dominant fragment is charge-2 (or
   modloss) still has its charge-1 b/y ions thresholded against that higher reference, even
   though the dominant ion itself is never written to the FI -- this is intentional: it reflects
   the real spectrum's shape rather than an FI-scope-dependent one.
4. **Minimum-fragment floor: keep the top `FRAGINDEX_CARAFE_MIN_KEPT_PEAKS` most intense
   eligible fragments, default 6**, regardless of the relative-intensity threshold, so a peptide
   with an unusually flat or low-confidence predicted spectrum never loses all its FI fragments.
   Not a fixed b/y split -- top-up pulls from the combined pool of length->=3-eligible b and y
   candidates by intensity, and a variant with fewer than 6 eligible fragments total simply keeps
   all of them (no padding). New named constant in `CometSearch/core/Constants.h`, next to the
   existing `FRAGINDEX_MIN_IONS_SCORE`/`FRAGINDEX_MIN_IONS_REPORT` (Section 4.2, step 4).
5. **Threshold is configurable, not hardcoded** -- a `carafe_ms2_to_fi_mask.py` CLI flag
   (`--min-relative-intensity`, default 0.10), alongside `--min-kept-peaks` for item 4's floor.
   Carafe's raw per-fragment intensity output is the durable artifact of the (expensive) GPU
   inference step; re-sweeping either the threshold or the floor re-reads it directly rather than
   re-running `ai_pred.py` -- needed for the T23/T24-style quality-vs-size comparison in Section 7
   regardless (Section 4.2).
6. **Mask generation is a separate offline Python tool**, not folded into `comet.exe -i`.
   `carafe_ms2_to_fi_mask.py` stays a standalone step reading Carafe's raw prediction output,
   distinct from Carafe's own inference step and from Comet's build CLI -- keeps Comet's C++ side
   free of any Python/Carafe dependency (matching `idx_to_carafe.py`'s existing design) and keeps
   the threshold/floor cheaply re-sweepable (item 5) without rerunning GPU inference.
7. **Phospho modloss channels are in scope now, not deferred.** This expands the feature beyond
   filtering: it requires adding a real neutral-loss b/y ion class to the FI itself (Section 5,
   pitfall 5; Section 6, Phase 2b), which today has none. Planned and tested as its own phase,
   gating the modloss-aware mask/threshold logic on it landing first.
8. **A PI_DB-shaped variant enumeration is required before Carafe can run, but not a second
   `.idx` file.** As actually implemented and validated (Section 6.13/6.14), the real workflow
   builds a single `.idx` with `comet.exe -i` (FI_DB -- the mask only ever applies to an FI_DB
   search), exports its variant enumeration with `comet.exe -x` (which internally forces a
   temporary PI_DB-mode read of that same FI_DB-tagged `.idx`, `bForceExportMode`, to reuse
   `EnumerateIndexPeptideMods()` rather than reimplementing it), then runs `idx_to_carafe.py` ->
   Carafe -> mask builder -> a masked search against that same `-i`-built `.idx`. Carafe still
   requires an already-enumerated peptide universe to predict against (unchanged from the
   original reasoning here), it's just produced by `-x`'s export rather than a separate PI_DB
   `.idx` build.
9. **Phase 2b's neutral-loss rule replicates Comet's existing classic-search mechanism
   exactly**, rather than inventing a new one -- grounded in reading `CometSearch.cpp`'s
   already-working fragment-NL code (Section 6.5) before asking the user anything: a single
   loss event per eligible fragment, gated on the *nearest* occurrence of the NL-bearing mod
   from the relevant terminus (first-from-N-term for b, first-from-C-term for y). Reuses
   `varModList[].dNeutralLoss`, already persisted in the `.idx` and already parsed by
   `idx_to_carafe.py` -- no format change needed for this decision alone.
10. **Primary neutral loss (`dNeutralLoss`) only for now; `dNeutralLoss2` deferred.** Carafe's
    phospho mode predicts a single `b_modloss`/`y_modloss` channel per ion type/charge, so a
    second FI loss series would have no predicted signal to mask it against.
11. **The FI inserts both the unshifted and the loss-shifted fragment as separate entries** at
    an NL-eligible position (matching classic search's own two-separately-binned-masses
    behavior), so Phase 2c's masking can independently keep/drop each based on Carafe's
    separate `b_z1` vs `b_modloss_z1` predicted intensities, rather than the loss-shifted mass
    replacing the unshifted one.
12. **`comet.exe -x` exports Comet's own canonical peptide-mod-variant enumeration**, rather
    than `idx_to_carafe.py` reimplementing `CometPeptideIndex::EnumerateIndexPeptideMods()`'s
    combinatorics a second time in Python (Section 6.10) -- decided when Phase 0.5 (an
    already-merged, unrelated master commit) stopped persisting `MOD_NUMBERS`/`MOD_SEQS`/the
    compact variant array in the `.idx` at all. A from-scratch Python reimplementation of that
    ~150-line, correctness-critical combinatorics engine would need re-deriving and
    re-verifying every time the C++ side changes; exporting instead makes the
    `(iWhichPeptide, modNumIdx, ...)` numbering match *by construction* (same code, same
    `.idx`, same `comet.params`, run twice) rather than by hoping two independent
    implementations stay in lockstep.
13. **Mask `.idx` fingerprint uses CRC-32 (zlib), not SHA-256** (Section 6.11) -- switched when
    Phase 3 needed to compute the identical fingerprint on both the Python (mask-build) and C++
    (mask-load) sides. This is a "did I point the mask at the wrong `.idx`" sanity check, not a
    security boundary, and zlib is already a linked dependency of Comet's C++ build that
    Python's `zlib` module wraps bit-for-bit identically -- a from-scratch/vendored SHA-256
    implementation matching bit-for-bit across two independent languages would have been new
    correctness-critical code for a check that only needs to catch accidental mismatches.
14. **A `VarModConfig` fingerprint closes the `modNumIdx`-validity gap the `.idx` fingerprint
    alone can't** (Section 6.10's closing note, closed in Section 6.11): since Phase 0.5,
    `modNumIdx` numbering depends on live `comet.params`' variable mods, not just the `.idx`,
    so a mask built against different variable mods than are live in the search consuming it
    could otherwise pass the `.idx` fingerprint check while carrying stale/meaningless
    `modNumIdx` keys. `comet.exe -x` serializes the active `variable_modNN` slots into one
    comparable string, propagated through `idx_to_carafe.py` and `carafe_ms2_to_fi_mask.py`
    into the mask file header, and `CometPredictedMask::Load()` rejects a mismatch loudly
    (search fails, specific error naming both configs) rather than relying solely on
    `Lookup()`'s "not found -> fully unfiltered" fallback to paper over it.
