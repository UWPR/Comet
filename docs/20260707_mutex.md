# Removing queriesMutex contention from the fused batch search hot path

Date: 2026-07-07
Status: **implemented** (verified against current code). `FusedSearchSpectrum` appends to a
per-worker `outQueries` vector with no lock (`CometPreprocess.cpp`'s `outQueries.push_back`),
and both `FusedLoadAndSearchSpectra` and a later-added sibling, `FusedPreloadThenSearch`, use
the `vSlotQueries`/`aQueryCount`/post-join-concatenation pattern from Sections 2-3 below
exactly as designed. `queriesMutex` itself was not deleted (Step 7's "leave it" branch was
taken) -- it remains declared in `SearchSession.h` and is still taken at three call sites, all
in the older, non-fused batch path (`LoadAndPreprocessSpectra`/`CheckExit`-adjacent code) this
doc's own Background section explicitly distinguishes from the fused path ("This is the same
architecture as the RTS path; it is NOT the old three-sweep `g_pvQuery`-mutex design"). The
fused path this doc targets is mutex-free on the hot path, as intended.
Scope: `CometSearch/CometPreprocess.cpp`, `CometSearch/CometPreprocess.h`,
`CometSearch/search/SearchSession.h` (batch FI_DB path only; RTS path untouched)

## 1. Background

`FusedLoadAndSearchSpectra` (CometPreprocess.cpp:3246) is the fused batch loader.
It launches `iNumThreads` worker jobs on the thread pool BEFORE the read loop
(CometPreprocess.cpp:3270-3278); each worker pops a `Spectrum` from a
`BoundedSpectrumQueue` and runs the full preprocess -> search -> post-analysis
pipeline in `FusedSearchSpectrum` (CometPreprocess.cpp:2953), using thread-local
scratch (`g_rtsScratch`, CometPreprocess.cpp:141). This is the same architecture
as the RTS path; it is NOT the old three-sweep `g_pvQuery`-mutex design.

Two contention points remain, both on `session.queriesMutex` (SearchSession.h:59):

1. Producer/consumer contention once per scan. The single reader thread takes
   `session.queriesMutex` on every spectrum read (CometPreprocess.cpp:3382-3389)
   only to call `CheckExit`. `CheckExit` actually reads the count solely when
   `g_staticParams.options.iSpectrumBatchSize != 0` (CometPreprocess.cpp:2008-2013);
   in the common case (`iSpectrumBatchSize == 0`) the lock is taken and
   `session.queries.size()` is read for nothing. Meanwhile all N workers take the
   same mutex once per completed `Query*` to `push_back` into `session.queries`
   (CometPreprocess.cpp:3235-3236). One single producer contends with N consumers
   on one mutex, once per spectrum on each side.

2. Shared-vector serialization. `session.queries` is one `vector<Query*>` appended
   by every worker. Downstream, Pipeline.cpp:184 does a single
   `std::sort(session.queries..., compareByScanNumber)` after the fused loop
   returns, so push order is irrelevant; nothing downstream depends on insertion
   order. The mutex is buying us nothing but a data-race guard on a shared vector
   we did not need to share.

Goal: remove `queriesMutex` from this hot path while producing byte-identical
output (the existing post-loop sort at Pipeline.cpp:184 already makes the result
order-independent of push order). Query* lifetime must be preserved: the pointers
outlive the fused loop and are freed later in `cleanupBatch` (Pipeline.cpp:157).

## 2. Design summary

- Give each worker its own `vector<Query*>` (indexed by the `iSlot` value already
  passed to `FusedSearchSpectrum`). Workers append lock-free to their own vector.
- After `tp->wait_on_threads()` returns (CometPreprocess.cpp:3399) -- the point at
  which all workers are provably done -- concatenate the per-slot vectors into
  `session.queries` in a single serial pass. Raw pointers move by value; ownership
  and lifetime are unchanged (still freed in Pipeline.cpp:157).
- Replace the producer's per-scan `size()` read with a lock-free running count:
  an `std::atomic<size_t>` incremented by workers, read by the producer only when
  `iSpectrumBatchSize != 0`. When `iSpectrumBatchSize == 0` the producer passes 0
  and never touches shared worker state at all.

This removes `session.queriesMutex` from every per-spectrum code path. The mutex
field can remain in `SearchSession` (still declared, now unused by the fused path)
or be deleted; see step 6.

### Step 4 -- per-slot vectors + atomic counter in `FusedLoadAndSearchSpectra`

File: `CometSearch/CometPreprocess.cpp:3267-3278` (worker launch block).

Add, just after `const int iNumSlots = g_staticParams.options.iNumThreads;`
(line 3267) and before/around the `BoundedSpectrumQueue queue(...)` line 3268:

```cpp
   const int iNumSlots = g_staticParams.options.iNumThreads;

   // Per-worker result vectors: each worker owns vSlotQueries[t] exclusively,
   // so no lock is needed on the append hot path.  alignas(64) prevents false
   // sharing of adjacent vector control blocks (ptr/size/capacity) during the
   // concurrent push_back storm.
   struct alignas(64) SlotVec { std::vector<Query*> v; };
   std::vector<SlotVec> vSlotQueries(iNumSlots);

   // Running count of accumulated Query* across all workers.  Only read by the
   // producer, and only when iSpectrumBatchSize != 0 (batch-size cap feature).
   std::atomic<size_t> aQueryCount{0};

   BoundedSpectrumQueue queue(static_cast<size_t>(iNumSlots) * 4);
```

Change the worker lambda (CometPreprocess.cpp:3270-3278) captures and call:
```cpp
   for (int t = 0; t < iNumSlots; ++t)
   {
      tp->doJob([&queue, t, &vSlotQueries, &aQueryCount]()
      {
         Spectrum spec;
         while (queue.pop(spec))
            FusedSearchSpectrum(std::move(spec), t, vSlotQueries[t].v, aQueryCount);
      });
   }
```

### Step 5 -- drop the producer's per-scan lock; feed count only when needed

File: `CometSearch/CometPreprocess.cpp:3382-3389`.

Before:
```cpp
      {
         std::lock_guard<std::mutex> lk(session.queriesMutex);
         if (CheckExit(iAnalysisType, iScanNumber, iTotalScans, iLastScan,
                       mstReader.getLastScan(), (int)session.queries.size(), 0))
         {
            break;
         }
      }
```
After:
```cpp
      // No lock: when iSpectrumBatchSize == 0 (the common case) CheckExit ignores
      // the count entirely, so pass 0.  When the batch-size cap is active, read the
      // lock-free running total.  This value is inherently approximate under
      // concurrency (the old locked read was too -- workers appended while the
      // producer held the lock), so relaxed ordering preserves existing behavior.
      {
         int iLoaded = (g_staticParams.options.iSpectrumBatchSize != 0)
                          ? (int)aQueryCount.load(std::memory_order_relaxed)
                          : 0;
         if (CheckExit(iAnalysisType, iScanNumber, iTotalScans, iLastScan,
                       mstReader.getLastScan(), iLoaded, 0))
         {
            break;
         }
      }
```

### Step 6 -- concatenate per-slot vectors after the join

File: `CometSearch/CometPreprocess.cpp:3398-3401`.

After `tp->wait_on_threads();` (line 3399) -- the barrier that guarantees every
worker has finished and will not touch its vector again -- append all slots into
`session.queries` in a single serial pass, then return:

```cpp
   queue.finish();
   tp->wait_on_threads();

   // All workers are now joined; their per-slot vectors are complete and no longer
   // mutated.  Concatenate into session.queries (ownership of the raw Query* moves
   // by value; they are freed later in Pipeline cleanupBatch).  Push order is
   // irrelevant: Pipeline.cpp sorts by scan number before writing.
   size_t iTotalQueries = 0;
   for (auto& slot : vSlotQueries)
      iTotalQueries += slot.v.size();

   session.queries.reserve(session.queries.size() + iTotalQueries);
   for (auto& slot : vSlotQueries)
   {
      session.queries.insert(session.queries.end(), slot.v.begin(), slot.v.end());
      slot.v.clear();
   }

   return !g_cometStatus.IsError() && !g_cometStatus.IsCancel();
```

Note: `session.queries.reserve(session.queries.size() + iTotalQueries)` is written
to be correct even if `session.queries` is non-empty on entry; in the current code
each batch starts from an empty/cleared `session.queries`, but reserving from the
current size is harmless and future-proof.

## 4. Points explicitly evaluated and deferred

### 4a. BoundedSpectrumQueue single-mutex (CometPreprocess.cpp:153-199) -- DEFER

The queue takes one mutex per `push` and one per `pop`, each critical section tiny
(a `std::move` of a `Spectrum` handle + a condvar notify). There is a single
producer whose throughput is gated by disk read + `PreloadIons` parse cost, which
is far more expensive than the lock acquire. At 20 threads the workers are almost
certainly starved by the producer, not blocked on the queue mutex. Recommendation:
DO NOT shard the queue pre-emptively. First measure (Section 5c). Only if
`perf lock` shows meaningful `queue.mtx` contention (i.e. the producer is not the
bottleneck) implement one of:
- per-worker SPSC ring buffers with round-robin push from the producer, or
- a lock-free MPMC queue.
Both add complexity and change the bounded-RAM guarantee (currently 4*iNumThreads
spectra in flight); defer until data justifies it.

### 4b. Per-charge-state `new Query()` / `new Results[iNumStored]` pool -- DEFER

Every accepted charge state does `new Query()` (CometPreprocess.cpp:3086) plus
`new Results[iNumStored]` (line 3117, plus decoys at 3132). At 20 threads * high
spectra/sec this is real heap churn. But a per-thread object pool does not fit the
current ownership model: the `Query*` lifetime extends past the fused loop -- the
pointers are handed to `session.queries` and freed only in Pipeline cleanupBatch
(Pipeline.cpp:157), after the batch is written. Within a single batch there is no
opportunity to recycle (every object is live until batch end). Pooling would only
help ACROSS batches, which exist only when `iSpectrumBatchSize != 0`; the common
`iSpectrumBatchSize == 0` case is one batch for the whole file, where a pool yields
zero reuse. Recommendation: DEFER. If a profiler later shows allocation as a hot
spot, the higher-value change is reducing per-`Results` allocations (the
`iNumStored`-sized array of objects each carrying `std::vector`/`std::string`
members that get `clear()`ed in the init loop at CometPreprocess.cpp:3147-3185),
not pooling `Query` itself.

## 5. Validation

### 5a. Correctness: identical output, old vs new

Because Pipeline.cpp:184 sorts `session.queries` by scan number before writing, the
`.txt`/`.pepXML` output must be byte-identical between old and new code for a fixed
input, EXCEPT where the format embeds nondeterministic tie-break order. Procedure:

```bash
# Build baseline (pre-change) binary.
git stash        # or build from the parent commit
make cclean && make
cp comet.exe /tmp/comet.old

# Build new binary.
git stash pop
make cclean && make
cp comet.exe /tmp/comet.new

# Run both on a fixed input at several thread counts.
for THREADS in 1 4 20; do
  for BIN in old new; do
    /tmp/comet.$BIN -Pcomet.params.high -N/tmp/out.$BIN.$THREADS \
        --num_threads=$THREADS fixed_input.mzML   # adjust flags to your params file
  done
  # Order-independent comparison of the two result tables.
  python tools/compare_txt_orderless.py /tmp/out.old.$THREADS.txt /tmp/out.new.$THREADS.txt
done
```

Comparison must be order-independent at the row level only if the writer order can
differ; since both paths sort by scan number, a direct `diff` of the `.txt` should
already match. If `diff` is clean, that is the strongest result. If it is not,
fall back to sorting both files by (scan, charge, xcorr, peptide) and diffing:

```bash
# Skip the two header lines, sort remaining rows canonically, diff.
tail -n +3 /tmp/out.old.20.txt | sort > /tmp/a.sorted
tail -n +3 /tmp/out.new.20.txt | sort > /tmp/b.sorted
diff /tmp/a.sorted /tmp/b.sorted && echo "IDENTICAL"
```

Run the existing suite as a regression gate:
```bash
python tests/unit/run_tests.py --comet /mnt/c/Work/Comet-master/comet.exe
```

Determinism check (must still hold): two independent runs of the NEW binary at
20 threads on the same input produce identical sorted output (analogue of T18).

### 5b. Benchmark: wall-clock at high thread count on a large batch

Use a >=100K-spectrum input. Report median of >=3 runs each.

```bash
for BIN in old new; do
  for i in 1 2 3; do
    /usr/bin/time -v /tmp/comet.$BIN -Pcomet.params.high \
        --num_threads=20 -N/tmp/bench.$BIN.$i big_100k.mzML 2>> /tmp/time.$BIN.log
  done
done
grep 'wall clock' /tmp/time.old.log /tmp/time.new.log
```

The `comet-benchmark` skill can also be used to report Hz / ms-per-spectrum for
old vs new side by side. Expect the gain to be modest in the `iSpectrumBatchSize==0`
common case (the removed lock is uncontended-cheap in absolute terms) but to widen
as thread count rises; the primary win is eliminated cache-line ping-pong on
`queriesMutex` and `session.queries`' growth pointer.

### 5c. Lock-contention measurement (proves the mutex is gone)

```bash
# Old binary: expect queriesMutex to appear as a contended lock.
perf lock record -- /tmp/comet.old -Pcomet.params.high --num_threads=20 \
    -N/tmp/lk.old big_100k.mzML
perf lock contention -t   # or: perf lock report

# New binary: queriesMutex contention should be gone; only queue.mtx (and any
# allocator locks) should remain.
perf lock record -- /tmp/comet.new -Pcomet.params.high --num_threads=20 \
    -N/tmp/lk.new big_100k.mzML
perf lock contention -t
```

Success criteria:
- `session.queriesMutex` no longer appears in the new binary's contended-lock list.
- Total contended lock wait time drops.
- If `queue.mtx` now dominates, that is the signal to revisit Section 4a; if it does
  not, the single queue is confirmed adequate and 4a stays deferred.

(If `perf lock` is unavailable in WSL, substitute `perf record -g` + flame graph and
confirm `__lll_lock_wait` / `pthread_mutex_lock` frames attributable to
`FusedSearchSpectrum` / the CheckExit block disappear.)

## 6. Risk notes

- Thread safety of the concatenation (Step 6) depends entirely on
  `tp->wait_on_threads()` being a true join barrier for the jobs launched at
  CometPreprocess.cpp:3270-3278. Confirm no worker can still be running after it
  returns (it is the same barrier the current code already relies on for
  `session.queries` to be complete). No new lifetime assumptions are introduced.
- `SlotVec` alignment (`alignas(64)`) is a defensive anti-false-sharing measure;
  it costs a few hundred bytes total and can be dropped if profiling shows it
  unnecessary. It does not affect correctness.
- Batch-size cap semantics (`iSpectrumBatchSize != 0`) are preserved but now read an
  atomic instead of a locked `size()`. Both are approximate snapshots under
  concurrency; the cap was never exact, so no behavior change for that feature.
- Out of scope: the MS1 batch path (`ms1Queries`) and the RTS path are untouched.
