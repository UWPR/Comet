# PI_DB RTS memory reduction, round 2: pooling the mod-permutation tables and compressing the variant array

Status: **Phases 0, 1, and 2 IMPLEMENTED (2026-08-27); Phases 3-4 planned.** Follow-up to
`docs/20260730_PI_reduction.md` (the DBIndex -> raw-table + compact-variant split,
implemented) and `docs/20260716_pidbmemory.md` (VarModSites compaction, implemented).
Target: **>= 25% additional reduction** in RTS PI_DB search-session memory. The plan below
projects **~40-60%** at the reference benchmark scale, with the first phase alone projected
to clear the 25% bar.

**Phase 2 implementation notes (2026-08-27).**

- Implemented as Section 4 describes: `g_vDBIndexVariants` (24B AoS + growth slack) became
  `g_dbIndexVariants` (`PiVariantArray`, core/Types.h) -- four exact-sized parallel arrays
  at 13B/entry with an `llround(mass * 1e4)` `uint32` key, `uint32` peptide index, `uint32`
  modNumIdx (`0xFFFFFFFF` = unmodified), and nibble-packed terminal mods.
  `GenerateVariantArray()` runs the enumeration twice (count, then fill into exact-sized
  staging), sorts the staging with the pre-Phase-2 element type/comparator (candidate
  ordering, ties included, provably unchanged), and transcodes to the SoA.
  `SearchPeptideIndex()` brackets on quantized keys widened 1 LSB per side
  (`QuantizeLow/High`), prefilters per entry via a new widening parameter on
  `CheckMassMatch(Query*, double, double dTolWiden = 0.0)` (so isotope-gap entries in a
  wide bracket are still rejected without materialization), then re-runs the exact,
  unwidened checks on `MaterializeOneEntry()`'s recomputed double mass -- which is
  bit-identical to the formerly stored value, so the accepted candidate set is unchanged.
- Beyond the plan, the staging transient was engineered away rather than accepted: Section
  4.2 budgeted a 37B/entry transcode transient (24B staging + 13B SoA); the implementation
  keeps it at ~24B/entry by (a) placing the staging in page-granular memory
  (`mmap`/`VirtualAlloc`; `AllocStagingPages()` et al., CometPeptideIndex.cpp) and
  progressively returning fully-transcoded staging pages to the OS
  (`madvise(MADV_DONTNEED)` / `VirtualFree(MEM_DECOMMIT)`) every 4M entries, and
  (b) `reserve()`+`push_back` (not `resize()`) on the SoA arrays, so their pages become
  resident only as they're written, in step with the staging's release. (b) was found by
  measurement, not foresight: the first cut used `resize()`, whose value-initialization
  touched all 1.5 GB up front and produced a 5.32 GiB transient peak -- worse than
  Phase 1's 4.36 GiB steady peak -- before the release logic could return anything.
- **Windows uses plain `malloc`/`free` for the staging, with no progressive release.** The
  first Windows implementation (VirtualAlloc + chunked `VirtualFree(MEM_DECOMMIT)`, the
  direct analogue of the POSIX path) built cleanly and then had `Comet.exe` **quarantined
  by CrowdStrike Falcon on its first execution**, reproducibly (rebuilt three times;
  removed within seconds of each exec attempt; Defender was confirmed off, Falcon
  confirmed the active AV) -- that alloc/decommit idiom is common in packers/loaders and
  evidently pattern-matches a behavioral heuristic. Swapping the Windows arm to
  `malloc`/`free` (identical POSIX arm) made the same-source rebuild run clean, 52/52.
  Windows therefore keeps a ~37B/entry transcode transient instead of ~24B/entry --
  still at or below its pre-Phase-2 steady state. If the machine's Falcon policy allows
  an exclusion for the build tree, the VirtualAlloc variant could be restored; not worth
  fighting by default.
- One real bug caught by the 8-config A/B harness (both PI multi-candidate arms suddenly
  produced zero PSMs; the t25 arms passed because `isotope_error = 0` short-circuits the
  affected path): a scripted rename inside `CheckMassMatch()` clobbered the new widened
  locals' own initializers into self-initialization (`const double dTolLow = dTolLow - ...`,
  an uninitialized read C++ accepts silently). Worth remembering as a reason the harness
  exists -- the unit suite alone (52/52 at the time) did not catch it, since no unit test
  runs PI_DB with isotope_error enabled.

Two structures dominate: the **variant array** and the **mod-permutation tables**. Both are
session-regenerated (never persisted -- Phase 0.5 of docs/20260730_PI_reduction.md), so every
change below is **in-memory only: no `.idx` format change, no version bump, no index rebuilds.**

### Key code facts the plan relies on (verified 2026-08-27)

1. **The per-variant `dPepMass` is only a candidate-selection key.**
   `CometSearch::SearchPeptideIndex()` (`CometSearch.cpp:2093-2180`) uses `variant.dPepMass`
   for the binary search, the window-exit check, the `g_massRange` clamp, and
   `CheckMassMatch()` -- then calls `CometPeptideIndex::MaterializeOneEntry()`
   (`CometPeptideIndex.cpp:747`), which **recomputes the exact mass** from
   `raw.dPepMass` + mod deltas, in the same order `EnumerateIndexPeptideMods()`'s `tryPush`
   computed it (`CometPeptideIndex.cpp:559-594`), so the recomputed double is bit-identical
   to the stored one. Everything downstream scores/reports the materialized mass. The stored
   key therefore doesn't need full double precision -- only enough to bracket candidates,
   with exactness restored per-candidate.
2. **All `MOD_NUMBERS` entries for one modifiable sequence are contiguous and equal-length.**
   `getModificationCombinations()` (`CometModificationsPermuter.cpp:753`) processes mod-seqs
   serially; `generateModifications()` records `[startModNum, count)` per seq into
   `MOD_SEQ_MOD_NUM_START/CNT`, and every entry's `modifications` array has length
   `modSeq.length()`. So a per-entry pointer is redundant: entry `m` of mod-seq `s` lives at
   a computable offset in a single flat pool.
3. **Every `MOD_NUMBERS` consumer already has the peptide (hence `modSeqIdx`) in hand:**
   `CometPeptideIndex.cpp:564/676/781` (tryPush, protein-filter check, `MaterializeOneEntry`),
   `CometFragmentIndex.cpp:506/605` (`AddFragmentsThreadProcRange`/`AddFragments`),
   `CometSearch.cpp:1671` (FI_DB scoring-path reconstruction). All read `(mods pointer, len)`
   and nothing else. A pooled accessor is a drop-in at all six sites.
4. **`lIndexProteinFilePosition` is consumed as a row index into `g_pvProteinsList`**, not a
   byte offset (`CometSearch.cpp:2282-2285`, `CometPeptideIndex.cpp:1164`) -- narrowable to
   `uint32_t` in the raw-peptide table.
5. **`FRAGINDEX_VMODS == 5`** (`core/Constants.h:77`): terminal-mod codes (-1..4) fit a nibble.
6. **`MOD_NUMBERS[].modifications[]` values are compacted-slot indices in -1..4** (same
   FRAGINDEX_VMODS bound): each fits a nibble too, enabling optional 2x pool packing.

## 3. Phase 1 -- flat-pool `MOD_NUMBERS` and `MOD_SEQS` (both search modes benefit)

**Projected saving at benchmark scale: ~1.5-2.5 GB (~25-38% of 6.58 GB).**

This is the follow-up docs/20260730_PI_reduction.md Section 3 already recommended, done
CSR-style like `ProteinsListCSR` (`core/Types.h:600`) and `VarModSites`
(docs/20260716_pidbmemory.md) before it: replace tens of millions of tiny heap objects with
one flat buffer plus computed offsets.

### 3.1 MOD_NUMBERS -> `g_modPool`

- `combine()` (`CometModificationsPermuter.cpp:417-481`) currently does
  `new char[modStringLen]` per accepted combination and pushes a 16-byte
  `ModificationNumber{len, ptr}`. Instead, append the `modStringLen` bytes to a single
  `vector<char> g_modPool` (reserve generously up front; it only grows by `modStringLen`
  per entry). Keep a running `MOD_NUM` exactly as today.
- Add `uint64_t* MOD_SEQ_POOL_START` (one per mod-seq, filled in
  `getModificationCombinations()` right where `MOD_SEQ_MOD_NUM_START[i]` is filled): the pool
  offset of that seq's first entry. Because entries for a seq are contiguous and equal-length
  (fact 2 above), entry `modNumIdx` of seq `modSeqIdx` is:

  ```cpp
  offset = MOD_SEQ_POOL_START[modSeqIdx]
         + (uint64_t)(modNumIdx - MOD_SEQ_MOD_NUM_START[modSeqIdx]) * modSeqLen;
  ```

- Accessor (in `CometPeptideIndex` or a small header both consumers include):
  `const char* GetModEntry(int modNumIdx, int modSeqIdx, int& iLenOut)`. Replace the six
  consumer sites (fact 3). `MOD_NUMBERS`/`ModificationNumber` are deleted outright --
  per-entry storage drops from ~40-56B (slot + chunk + allocator metadata) to exactly
  `modStringLen` bytes (~4-8 typical).
- `PassesVarModProteinFilter()` (`CometPeptideIndex.cpp:535`) already takes
  `(const char*, int)` -- unchanged.
- Note `CometSearch.cpp:1657-1674` (FI_DB path) currently copies
  `ModificationNumber modNum = MOD_NUMBERS.at(...)` **by value** and
  `string modSeq = MOD_SEQS.at(...)` **by value per candidate** -- the rewrite to
  pointer+length also deletes a per-candidate heap copy from FI_DB's scoring hot path.

### 3.2 MOD_SEQS -> flat pool

Same treatment: one `vector<char>` + `uint32_t` offsets array (`numModSeqs + 1`; length =
offset delta, which also supplies `modSeqLen` for the 3.1 arithmetic with no per-entry
storage at all). The build-time dedup map in `getModifiableSequences()`
(`CometModificationsPermuter.cpp:281`) stays a transient `unordered_map` keyed on
`string_view`-into-pool or temporary strings -- it's freed before search. Consumers switch
from `const string&` to `(const char*, int)`; `MaterializeOneEntry()`'s
`(size_t)j >= modSeq.size()` guard (`CometPeptideIndex.cpp:801`) becomes `j >= iModSeqLen`,
same semantics.

Saves ~0.05-0.13 GB (string headers + allocator overhead) -- small, but it makes 3.1's
length arithmetic self-contained and removes the FI per-candidate string copy above.

### 3.3 Optional (defer): nibble-pack the pool

Mod values are -1..4 (fact 6): two per byte with 0xF as the -1 sentinel halves the pool
(~0.1-0.2 GB more). Adds decode cost to `MaterializeOneEntry()`'s per-candidate loop and
complicates `PassesVarModProteinFilter`. Only do this if Phase 0's numbers show the pool
itself (not the overhead Phase 1 removes) is significant. Default: skip.

### Lifecycle note

Today's `MOD_NUMBERS[].modifications` allocations are deliberately never freed (see the
PROCESS-LIFETIME warning at `CometPeptideIndex.cpp:411-431`). The pool keeps that lifecycle
(build once per process, never torn down) -- do **not** use Phase 1 as an excuse to wire up
partial teardown; the warning about `GetVModSlotForAllModsIdx()`'s magic static still applies
verbatim. The pool merely makes an eventual clean teardown *possible* (2 frees instead of
~50M).

## 4. Phase 2 -- PI variant array: SoA layout, 4-byte fixed-point mass key, exact sizing

**Projected saving at benchmark scale: ~1.3-2.4 GB (structural 2.79 -> 1.51 GB, plus the
0.5-1.2 GB growth slack eliminated).** PI_DB-only: replaces `g_vDBIndexVariants`;
`g_vFragmentPeptides` (FI_DB) is untouched (candidate for later adoption).

### 4.1 Layout

Replace `vector<FragmentPeptidesStruct>` (24B AoS) with a structure-of-arrays
`PiVariantArray` (13B/entry, no padding by construction):

| Array | Type | Encodes |
|---|---|---|
| `puiMassKey` | `uint32_t` | `(uint32_t)llround(dPepMass * 1e4)` -- fixed-point 1e-4 Da. Monotonic under the exact-mass sort, so binary search semantics are preserved. Covers masses to 429,496 Da; assert `dPeptideMassHigh` fits at build. Quantization error <= 5e-5 Da, far below any usable tolerance. |
| `puiWhichPeptide` | `uint32_t` | as today (already bounded to `unsigned int` by the `CreateFragmentIndex()` check, `CometFragmentIndex.cpp:116`; add the same check on the PI path). |
| `puiModNumIdx` | `uint32_t` | `0xFFFFFFFF` = unmodified (today's -1). |
| `pucTermMods` | `uint8_t` | hi nibble `cNtermMod + 1`, lo nibble `cCtermMod + 1`, 0 = none (fits: FRAGINDEX_VMODS = 5). |

### 4.2 Build: byte-identical ordering by construction

Candidate *ordering* is observable: equal-mass entries are scored in array order, and
`std::sort` is unstable, so any change to element size/comparator can permute ties and
perturb tie-broken output. To keep the change provably inert:

1. Run `EnumerateIndexPeptideMods()` once in **count-only** mode (same enumeration + mass
   filter, just a counter -- the lambda already computes the mass; ~doubles enumeration time,
   which is a one-per-session cost measured in seconds at this scale).
2. `reserve()` the staging `vector<FragmentPeptidesStruct>` **exactly** and fill it with
   today's unchanged code path, sort with today's comparator -- identical input sequence,
   identical comparator, identical `std::sort` => identical final order, ties included.
3. Transcode into the SoA arrays (exact-sized), then free the staging vector.

Steady-state cost is 13B/entry. Transient peak during transcode is 24B + 13B = 37B/entry,
still below today's steady 36-48B/entry (24B x 1.5-2x capacity slack), so peak memory never
regresses either. (A later optimization can sort the SoA directly via an index permutation
with an explicit total-order tiebreak `(mass, iWhichPeptide, modNumIdx, termMods)` -- that
changes tie order once, deliberately, and would actually *improve* cross-platform
determinism; keep it out of this change so the A/B diff stays byte-identical.)

### 4.3 Search-side changes (`CometSearch::SearchPeptideIndex`, `CometSearch.cpp:2093`)

- Binary search on `puiMassKey` with `uiKeyLow = (uint32_t)floor(dMassTolLow * 1e4) - 1`
  (saturating), window exit at `uiKeyHigh = (uint32_t)ceil(dMassTolHigh * 1e4) + 1` -- the
  +-1 LSB widening makes bracketing strictly conservative w.r.t. quantization.
- The `g_massRange` clamp and `CheckMassMatch()` prefilter (`CometSearch.cpp:2134/:2153`)
  run against the **dequantized key with tolerance widened by +-1e-4 Da** -- cheap per-entry
  rejection stays, so the isotope-offset window structure (narrow slivers inside a several-Da
  bracket) does not cause mass materialization of everything in the bracket.
- After `MaterializeOneEntry()` succeeds, re-run the **exact** `CheckMassMatch()` /
  `g_massRange` checks against `dbiLocal.dPepMass` (bit-identical to today's stored double,
  fact 1). Net effect: the accepted candidate set and all scores are identical to today;
  the only extra work is materializing candidates within 1e-4 Da of a window edge that then
  fail the exact check -- vanishingly rare.
- The per-candidate `strlen(g_vRawPeptides[...].szPeptide)` length filter at
  `CometSearch.cpp:2147` is unchanged here (Phase 3 removes the strlen).

### 4.4 Rejected deeper cut (documented for the record)

Dropping the mass key entirely and replacing the binary search with a bucket directory
(`uint64_t` start offset per 0.001-Da bin, ~34 MB for a 700-5000 Da range -- the same CSR
trick `g_iFragmentIndexOffset` uses) would reach 9B/entry (~0.5 GB more saved). Rejected for
this round: without a per-entry key, every entry inside the bracketing bins -- including the
isotope-gap dead zones -- must be materialized (or have its mass recomputed) just to be
rejected, which is a real CPU regression risk on wide-tolerance/isotope searches, for a
modest additional win. Revisit only if Phase 0/2 measurements say the remaining 1.5 GB
matters.

## 5. Phase 3 -- raw-peptide table: sequence pool + field narrowing

**Projected saving: ~0.15-0.18 GB at benchmark scale (secondary), but ~6-8 GB at
no-enzyme/MHC scale (~190M raw peptides), where this array dominates PI_DB memory.**

`PlainPeptideIndexStruct` (72B) spends 51B on `szPeptide[MAX_PEPTIDE_LEN]` (avg ~15 used) and
8B on a protein-list *row index* stored as `comet_fileoffset_t` (fact 4). Replace
`g_vRawPeptides` with a `RawPeptideTable`:

- one flat `vector<char>` sequence pool (no NUL terminators; lengths from offsets);
- SoA fields: `double dPepMass` (8), `uint32_t` seq-pool offset (4; pool > 4 GB is
  unreachable -- 190M x 50 max = 9.5 GB would overflow, so use `uint64_t` offsets iff
  `pool size > UINT_MAX`, decided at load; or simply store `uint40`-style split -- keep it
  simple: `uint64_t` costs 4 more bytes and is still a big win, decide by measurement),
  `uint32_t` protein row index (4), `uint16_t siVarModProteinFilter` (2),
  `char cPrevAA, cNextAA` (2), `uint8_t len` (1);
- accessor returns a lightweight view (`const char* pSeq`, `int iLen`, plus the scalar
  fields) so the ~139 `szPeptide` consumer sites migrate mechanically; `strcpy(out.sPeptide,
  raw.szPeptide)` in `MaterializeOneEntry()` becomes `memcpy` + NUL.

~72B -> ~21-25B + ~15B pool = **~36-40B/entry**, and the stored length deletes the
per-candidate `strlen` in `SearchPeptideIndex()`'s window scan (`CometSearch.cpp:2147`) and
in `MaterializeOneEntry()` (`CometPeptideIndex.cpp:764`) -- a minor CPU win in the hot path.

Scope warning: this touches the shared build path (`GeneratePlainPeptideIndex()`'s per-thread
tuples and the `.idx` writer read it), the load path (`ReadPeptideIndex()`,
`CometPeptideIndex.cpp:174-223`, which can decode straight into the pool -- the on-disk
records are already variable-length, so **no format change**), FI_DB's `AddFragments`, and
every output writer that prints sequences. It is the largest-diff phase; that's why it's
third despite being the top win for non-tryptic workloads. The existing 5-bit packing
machinery (`PackPeptide`, `core/Types.h:468`) could halve the pool later; not part of this
round.

## 6. Phase 4 (optional, defer by default) -- protein list and name cache

- `ProteinsListCSR::m_flat` stores 8B file offsets; protein-name blocks are fixed
  `WIDTH_REFERENCE` (=256, `core/Constants.h:68`) strides in one contiguous section, so a
  `uint32_t` ordinal + section base reproduces the offset. Halves `m_flat`.
- `g_pvProteinNameCache` (`unordered_map<comet_fileoffset_t, string>`) becomes a
  `vector<string>` indexed by that ordinal -- deletes per-node map overhead and hashing on
  the RTS protein-name lookup path.

Tens of MB at tryptic scale; only worth doing opportunistically or at MHC scale. Note the
decoy-classification dependency on this cache (CLAUDE.md Key Globals table) -- any change
here must re-run the decoy-mode tests (T23).

### 7.1 FI_DB applicability

Three of the four phases help FI_DB automatically, because the structures they compress are
shared between the two search modes; one is PI-only as scoped but portable:

- **Phase 1 -- full benefit, no extra work.** `MOD_NUMBERS`/`MOD_SEQS` are one set of
  globals consumed by both modes (FI_DB reads them in `AddFragments`/
  `AddFragmentsThreadProcRange`, `CometFragmentIndex.cpp:506/605`, and in the scoring-path
  candidate reconstruction at `CometSearch.cpp:1671`). The ~1.5-2.5 GB saved is the same
  absolute number for FI_DB -- roughly 8-13% of its 19 GB baseline; it is in fact FI_DB's
  own ~2 GB predicted-vs-measured gap from docs/20260730_PI_reduction.md Section 1. FI_DB
  additionally gets a small CPU win: its scoring path currently copies a
  `ModificationNumber` struct and a `std::string modSeq` *by value per candidate*
  (`CometSearch.cpp:1657-1674`); the pointer+length rewrite deletes that per-candidate heap
  copy from the hot loop.
- **Phase 3 -- full benefit.** `g_vRawPeptides` is shared; FI_DB reads it during index
  generation and per scored candidate (`strcpy` from `szPeptide`, `CometSearch.cpp:1654`).
  Modest at tryptic scale, large for no-enzyme/MHC databases in both modes.
- **Phase 4 -- shared**, since both modes use `g_pvProteinsList`/`g_pvProteinNameCache` for
  protein reporting and decoy classification.
- **Phase 2 is PI-only as scoped** (it replaces `g_vDBIndexVariants`), but FI_DB's
  `g_vFragmentPeptides` is structurally identical (24B x the same variant count = 2.79 GB
  at benchmark scale), so the 13B/entry SoA treatment is portable later. Two reasons it is
  deferred rather than included: (a) FI_DB's posting list (`g_iFragmentIndex`) stores
  indices into that array, so every access site changes; and (b) FI_DB's scoring path uses
  the *stored* `dPepMass` directly as the reported calculated mass (`CometSearch.cpp:1663`)
  with no equivalent of PI_DB's `MaterializeOneEntry()` exact-mass recompute -- quantizing
  the stored mass there changes output values unless FI_DB first grows the same recompute
  step. **Porting condition:** add an exact-mass recompute (the `raw.dPepMass` + mod-delta
  sum `tryPush`/`MaterializeOneEntry` already implement) to the FI_DB candidate
  reconstruction at `CometSearch.cpp:1663`, then adopt the SoA layout; until then FI_DB
  keeps the 24B AoS.

Perspective on the FI_DB ceiling: FI_DB's dominant cost is the fragment-ion posting list
itself (~13.8 GB of the 19 GB), which none of these phases touch. Phases 1+3+4 get FI_DB
roughly 10-15% total, versus 50%+ for PI_DB.

## 8. Correctness invariants and risks

1. **Byte-identical output is the acceptance bar** for Phases 1-3 (same methodology as
   docs/20260730_PI_reduction.md: full-scale real `.raw` + real-database PI_DB run, diff all
   PSM rows/columns pre- vs. post-change). Phase 1 is a pure representation swap (same bytes,
   new address) -- identical by construction. Phase 2's staging-sort keeps candidate order
   (ties included) and the exact-mass recompute keeps acceptance decisions identical
   (Section 4.2/4.3). Phase 3 changes no values, only storage.
2. **Quantization safety**: the +-1 LSB bracket widening plus post-materialization exact
   check means the fixed-point key can only ever *admit* extra borderline candidates into
   the exact check, never lose one. Assert at build: `dPeptideMassHigh * 1e4 < UINT32_MAX`.
3. **Thread safety unchanged**: every new structure is built inside
   `ReadPeptideIndex()`/session init, before any search thread starts, and is read-only
   afterward -- same contract as the structures it replaces (CLAUDE.md Key Globals table).
   Update `docs/GlobalVariables.md` and the CLAUDE.md table when globals are renamed.
4. **Process-lifetime semantics preserved**: no partial teardown of the mod tables/pools
   (Section 3's lifecycle note); the `g_bPeptideIndexRead` re-entry guards stay as-is.
5. **No `.idx` format change in any phase** -- everything touched is regenerated per session
   (variants, mod tables) or built at load from unchanged on-disk records (raw table).
   No baseline-index invalidation, no version bump.
6. **Perf risk is low but must be measured**: binary search + window scan move to smaller,
   SoA, cache-friendlier arrays (likely neutral-to-faster); the count-only enumeration pass
   adds seconds to session init; Phase 1 removes ~50M allocations from init. Confirm with
   the `comet-benchmark` skill's RTS methodology (pure search-call Hz + wall clock, before
   and after each phase), and watch T23/T24's `_check_timing`.
7. **Stale comments**: `SearchPeptideIndex()`'s comments still say `g_vDBIndexVariants` is
   "read directly off disk" (pre-Phase-0.5 wording) -- fix while editing that function.
